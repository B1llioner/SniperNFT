# Rust: тест десяти последовательных окон минта

## Цель и текущий статус

Команда разворачивает собственную тестовую NFT-коллекцию и фабрику в Robinhood Chain, chain ID **4663**. Для каждого выбранного транспорта она пытается отправить **10 транзакций с интервалом в одну секунду, по 10 NFT в каждой**, и проверяет, попала ли каждая в первый допустимый L2-блок своего окна.

При `--transport both` серии идут последовательно: сначала HTTPS, затем WSS, с отдельной коллекцией и фабрикой для каждой серии. Это **26 транзакций**: по два деплоя, один `arm` и десять минтов на транспорт. Максимальный результат — 200 NFT на одном кошельке. Одному транспорту соответствуют 13 транзакций и максимум 100 NFT.

Десять секунд — длительность десяти окон минта. Деплой, ожидание старта, получение receipts и проверка результата занимают дополнительное время. Проверки `ownerOf` и заголовков после серии ограничены паузами 100 ms; они не входят в измеренный интервал отправки.

**Статус на 16 сентября 2026: CLI установлен на выбранном EC2; обе серверные симуляции прошли. Платный mainnet-запуск ещё не выполнен.** Приватный ключ вводит пользователь в скрытом терминальном запросе. Пройдены 46 Rust-тестов и 13 локальных EVM-сценариев, включая перезапуск после неопределённой отправки. [Ревью кода](../research/REAL_TX_CODE_REVIEW.md), [ревью установки](../research/REAL_TX_INSTALL_REVIEW.md).

Ожидаемый публичный адрес для планируемого запуска: `0x59Cd658EB1be492c52CcAA2575A90A236F77fAE2`. Расчётный баланс — **0.02 ETH**; актуальный баланс проверяется через RPC перед отправкой.

## Готовый запуск на EC2

Откройте [AWS CloudShell в Ohio](https://us-east-2.console.aws.amazon.com/cloudshell/home?region=us-east-2) и выполните:

```bash
aws ssm start-session --region us-east-2 --target i-0ef42c1e5475d7edb
```

Уже внутри EC2, от `ssm-user`, для двух серий — HTTPS и WSS:

```bash
vinos-real-tx both
```

Дождитесь `Private key (hidden, not saved):`, вставьте ключ указанного кошелька и нажмите Enter. Не вставляйте ключ в команду или чат. Держите сессию открытой до итогового отчёта. Для одной серии вместо `both` укажите `https` или `wss`.

Launcher: `/usr/local/bin/vinos-real-tx`. Бинарник установлен в отдельную версию `/opt/vinos-real-tx/<artifact-sha256>/bin/rust-mint-benchmark`; launcher указывает на проверенную версию. Отчёт двух серий: `/var/lib/vinos-real-tx/run-both-001/`. Повторный запуск в ту же директорию запрещён; при ошибке сначала сверяют журнал.

Серверный preflight подтвердил баланс 0.02 ETH, симуляцию 10 NFT и estimate **1 560 422 gas** на батч. При проверенной комиссии максимальный резерв на оба маршрута составил **0.0154702232 ETH**; это верхний расчёт по gas limits, не фактический расход. Перед вводом ключа и отправкой расчёт обновляется. Общий предел launcher — 0.019 ETH, остаток — минимум 0.001 ETH. Read-only wrapper `preflight` уже выполнен при установке; его фиксированная директория существует.

## Транспорты и измерения

| Режим | Маршрут отправки по умолчанию | Что сравнивается |
| --- | --- | --- |
| `https` | `https://sequencer.mainnet.chain.robinhood.com` | JSON-RPC `eth_sendRawTransaction` напрямую официальному секвенсору |
| `wss` | `wss://robinhood-rpc.publicnode.com` | JSON-RPC `eth_sendRawTransaction` через WSS RPC-провайдера |
| `both` | Оба маршрута последовательно | Две отдельные серии с одинаковой формой транзакций |

Официальный адрес секвенсора, chain ID и публичный reader перечислены в [документации Robinhood](https://docs.robinhood.com/chain/connecting/). Адрес `wss://feed.mainnet.chain.robinhood.com` предназначен для получения sequencer feed; этот CLI не использует его для отправки транзакций.

HTTP-клиент и его пул соединений переиспользуются, WSS использует одно открытое соединение в серии. Во время ожидания выполняется прогрев. Подготовленные подписи существуют до старта окон. WSS-клиент реализован через `tokio-tungstenite`; собственный низкоуровневый WebSocket codec из другого транспортного бенчмарка здесь не задействован. При неоднозначном результате отправки клиент автоматически не переподключается и не повторяет транзакцию.

Reader по умолчанию — `https://rpc.mainnet.chain.robinhood.com`; чтения отделены от sender. Для preflight reader должен поддерживать `eth_call` и `eth_estimateGas` с state overrides, а для проверки — чтения блоков и состояния по номеру блока. Публичные endpoints имеют ограничения частоты запросов; можно указать свой `--read-rpc` и `--wss-url`. [Поддерживаемые endpoints](https://docs.robinhood.com/chain/connecting/).

HTTPS напрямую к секвенсору и WSS через провайдера проходят разные сетевые маршруты. Разница их результатов не доказывает преимущество одного протокола сама по себе.

### Как определяется первый блок

Для раунда `r` контракт разрешает минт при `startTime + r <= block.timestamp < startTime + r + 1`. CLI планирует отправку по локальным часам, а решение о допустимости принимает контракт по времени блока.

В отчёте используются **L2-номера из JSON-RPC receipts и заголовков**. Solidity `block.number` на Arbitrum L2 отражает приблизительный номер блока Ethereum; он не подходит для счёта быстрых L2-блоков. Это различие описано в [документации Arbitrum](https://docs.arbitrum.io/arbitrum-essentials/arbitrum-vs-ethereum/block-numbers-and-time).

Для целевой секунды `T` отчёт сохраняет соседние заголовки `previousBlock` и `firstEligibleBlock` и проверяет:

```text
previous.number + 1 == first.number
first.parentHash == previous.hash
previous.timestamp < T <= first.timestamp
```

Receipt должен соответствовать каноническому блоку, прочитанному при анализе. `hitFirstBlock` требует фактического минта, включения именно в `firstEligibleBlock` и timestamp этого блока, равного `T`. Если первый блок появился уже после секундного окна, это не считается попаданием. Позиция транзакции внутри блока выводится отдельно как `transactionIndexZeroBased`.

`rpcAckMs` измеряет ответ sender на отправку. `receiptObservedAfterSendMs` измеряет первое наблюдение receipt через reader и включает RPC-задержку и ожидание очереди опроса. Observer выполняет один запрос раз в 100 ms, перебирая ожидаемые hashes: при десяти pending-транзакциях к одному hash возвращается примерно раз в секунду плюс сетевое время. Эти величины не являются точным временем исполнения или подтверждением финальности. При десяти наблюдениях nearest-rank p95 и p99 равны максимуму выборки; такой объём не даёт устойчивой оценки редких задержек.

Команды выполняются из корня репозитория. Нужен Rust **1.93 или новее** согласно `rust-version` в manifest.

```bash
cargo build --manifest-path rust-mint-benchmark/Cargo.toml --release --locked
./rust-mint-benchmark/target/release/rust-mint-benchmark --help
```

Бинарник включает ABI, bytecode, runtime bytecode и storage layout из [`artifacts/timed-benchmark.json`](../artifacts/timed-benchmark.json). Артефакт соответствует Solc **0.8.26**, Shanghai, optimizer runs 200. Загрузка проверяет SHA-256 исходников; после изменения Solidity артефакт нужно пересобрать:

```bash
npm ci
node scripts/compile-timed-benchmark.mjs
```

## Сначала проверка без отправки

Каждый `--output` должен обозначать **новую, ещё не существующую директорию**. Родительская `.state` должна существовать.

```bash
mkdir -p .state
./rust-mint-benchmark/target/release/rust-mint-benchmark \
  --wallet 0x59Cd658EB1be492c52CcAA2575A90A236F77fAE2 \
  --transport both \
  --output .state/timed-mint-preflight-001
```

Без `--send` команда не запрашивает ключ и не отправляет транзакции. Preflight проверяет сеть, EOA, nonce, баланс, комиссию, лимиты газа, связь с sender и реальный путь минта через виртуальные runtime-контракты в state overrides. Он требует, чтобы `eth_call` вернул фактический минт всей запрошенной партии, затем проверяет estimates с запасом 20%. Эти overrides не создают контрактов в сети.

Если RPC не поддерживает нужную симуляцию или условия не выполняются, preflight завершает команду с ошибкой до отправок. Он также требует, чтобы локальные часы и последний блок расходились не больше чем на пять секунд.

Для live-запуска на Linux дополнительно требуется внешняя проверка синхронизации через `chronyc` с допустимой погрешностью не более **20 ms**. Read-only preflight эту проверку не требует. Изменение локальных часов во время серии также проверяется; скачок часов делает результат непригодным для сравнения.

## Запуск с отправкой

Команда ниже является инструкцией для будущего запуска. Она **расходует ETH** на новые тестовые контракты и транзакции.

```bash
./rust-mint-benchmark/target/release/rust-mint-benchmark \
  --wallet 0x59Cd658EB1be492c52CcAA2575A90A236F77fAE2 \
  --transport both \
  --quantity 10 \
  --start-delay-seconds 30 \
  --send-offset-ms 0 \
  --max-total-cost-eth 0.019 \
  --reserve-eth 0.001 \
  --lock-dir .state/real-tx-locks \
  --output .state/timed-mint-live-001 \
  --send
```

После первого preflight программа запросит приватный ключ **скрытым вводом в терминале**. Ключ должен соответствовать `--wallet`. Он не передаётся аргументом командной строки, переменной окружения или конфигурационным файлом и не записывается в отчёт. Ключ и подписанные raw transactions не нужно отправлять в чат.

Далее выполняются свежий preflight, деплой, проверка runtime-кода, финальная симуляция пути минта и `arm`. Время старта устанавливается после подготовки; все десять транзакций подписываются заранее. У каждой серии собственный случайный `runId`, коллекция и фабрика. Новый запуск создаёт новую серию, повторное использование старой фабрики этим CLI не предусмотрено.

Для одного маршрута измените `--transport both` на `https` или `wss`. Для RPC-провайдера с другим адресом добавьте `--read-rpc` и/или `--wss-url`. Используйте один live-процесс на кошелёк: `--lock-dir` должен быть общим для запусков на данном сервере. Файловый lock не координирует другие машины или внешние приложения кошелька.

### Настройки и жёсткий бюджет

| Параметр | По умолчанию | Допустимые значения / смысл |
| --- | --- | --- |
| `--quantity` | `10` | 1–10 NFT на транзакцию; число раундов всегда 10 |
| `--start-delay-seconds` | `30` | 15–120 секунд запаса после подготовки серии |
| `--send-offset-ms` | `0` | 0–900 ms после начала целевой секунды |
| `--fee-multiplier` | `4` | 1–10; множитель для `max(eth_gasPrice, baseFeePerGas)` |
| `--batch-gas-limit` | `3000000` | 1 000 000–10 000 000; дополнительно проверяется estimate и лимит сети |
| `--receipt-timeout-seconds` | `30` | 5–120 секунд ожидания receipt |
| `--max-total-cost-eth` | `0.019` | Положительное значение **не выше 0.019 ETH** за весь запуск |
| `--reserve-eth` | `0.001` | Остаток **не ниже 0.001 ETH** |

Все транзакции имеют `value = 0`, тип EIP-1559 и `maxPriorityFeePerGas = 0`. Верхняя комиссия фиксируется свежим планом до отправки. Лимиты газа для деплоя каждого контракта — 2 000 000, для `arm` — 150 000. При стандартном батче сумма подписанных лимитов составляет:

```text
Один маршрут: 2 × 2 000 000 + 150 000 + 10 × 3 000 000 = 34 150 000 gas
Оба маршрута: 68 300 000 gas
Резерв расходов = сумма gasLimit × maxFeePerGas
```

Перед отправкой резерв расходов должен укладываться в 0.019 ETH, а вместе с отдельным остатком — в фактический баланс. При 0.02 ETH это оставляет минимум 0.001 ETH. Если свежая комиссия не помещается в бюджет, программа прекращает запуск; она не увеличивает лимит автоматически. Резерв — расчёт верхней границы, а фактические расходы считаются по receipts. Внешние операции этого кошелька в данный бюджет не входят.

## Отчёт и остановка

По умолчанию действует `--failure-policy first-block`: успешный раунд должен сминтить всю запрошенную партию в первом L2-блоке своей секунды. **Три неудачных раунда подряд останавливают новые отправки и весь запуск**, включая ещё не начатый второй транспорт. Успех сбрасывает счётчик. Альтернатива `--failure-policy no-mint` считает неудачей только отсутствие фактического минта: даже частичный минт сбрасывает счётчик, а попадание в первый блок остаётся отдельной метрикой отчёта.

Receipts и соседние заголовки проверяет отдельный фоновый reader; счётчик обновляется в порядке раундов, даже если результаты пришли в другом порядке. Перед очередной отправкой CLI проверяет готовое решение без ожидания RPC. Если накопилось три отправленных раунда без полной последовательной классификации, он также останавливается с `FEEDBACK_LAG`: неизвестные результаты не записываются как доказанные неудачи. Уже отправленные транзакции могут исполниться после остановки.

При остановке сохраняется `diagnostics.json`: причина, события минта, hashes, целевые/фактические блоки, задержки отправки и ACK. Предварительный `diagnostics-preliminary.json` записывается до дополнительного RPC-анализа, чтобы сбой reader не стёр имеющиеся данные. CLI не перезапускает тест и не меняет настройки автоматически. Потерянный ACK, ошибка RPC или сбой часов по-прежнему прекращают отправки сразу, без ожидания трёх неудач.

| Файл | Содержимое |
| --- | --- |
| `initial-plan.json` | План до ввода ключа; только в live-режиме |
| `plan.json` | Актуальный план, адреса, комиссия, резерв расходов и симуляции |
| `journal.jsonl` | Durable intents с hash/nonce, ACK, receipts и причины остановки |
| `diagnostics.json` | Подробная причина досрочной остановки и данные для её разбора |
| `diagnostics-preliminary.json` | Данные до дополнительного RPC-анализа; остаются доступны, даже если анализ завершился ошибкой |
| `https-sequencer.json` | Результат законченной HTTPS-серии |
| `wss-rpc-provider.json` | Результат законченной WSS-серии |
| `result.json` | Итог всех выбранных серий, расходы и общий критерий результата |

До первой записи `intent` создаётся постоянный маркер `4663-<wallet>.pending.json` в `--lock-dir`; затем до каждой отправки hash и nonce сохраняются в журнале. Маркер указывает на директорию отчёта и блокирует следующий live-запуск даже с новым `--output`. Отчёт содержит адреса фабрик и коллекций; отдельного ручного поиска после деплоя не требуется. При аварийной остановке часть итоговых файлов может отсутствовать, поэтому отправной точкой служит `journal.jsonl`.

Коды завершения:

- **0:** read-only preflight успешен либо все десять полных батчей каждого выбранного транспорта попали в первые допустимые блоки.
- **2:** live-замер завершён, но хотя бы один батч неполный или не попал в первый блок.
- **1:** ошибка, остановка или неполная серия; перед следующим live-запуском требуется проверить журнал и состояние сети.

Таймаут, потерянный ACK, другой hash в ответе или прерывание не доказывают, что транзакция не принята. CLI прекращает дальнейшие отправки при неоднозначном результате и не повторяет raw transaction автоматически. Проверьте все подготовленные hashes, receipts и `latest`/`pending` nonce кошелька. После полного завершения и сохранения результата программа снимает pending-маркер; после аварии его можно удалить вручную только после сверки всего незавершённого запуска. Новый `--output` не обходит этот запрет.

## Контракты: область доверия и инварианты

Исходники: [`TimedBenchmarkNFT.sol`](../contracts/TimedBenchmarkNFT.sol), [`TimedBenchmarkBatchMinter.sol`](../contracts/TimedBenchmarkBatchMinter.sol). Это отдельные контракты для собственной тестовой коллекции; Rare Friends Genesis в этом бенчмарке не вызывается.

- Коллекция имеет неизменяемого владельца, `MAX_SUPPLY = 10000`, десять окон и однократный `arm` только от владельца. Административного обхода лимита и upgrade-механизма нет.
- `mint(round)` доступен в активную секунду при наличии остатка. `hasMinted(msg.sender)` сохраняется навсегда: передача NFT не восстанавливает право адреса на минт.
- Фабрика имеет неизменяемые owner, collection и recipient. Она принимает только вызовы владельца и защищена от повторного входа. CLI дополнительно сверяет развёрнутый runtime с ожидаемым артефактом.
- В начале активной попытки фабрика читает оставшийся supply и ограничивает количество перед созданием helpers. Если другие транзакции успели раньше, она минтит доступный остаток. Чужие транзакции не могут вклиниться между чтением остатка и действиями внутри одной атомарной транзакции.
- Для каждого NFT создаётся новый helper. Его конструктор минтит одну штуку, проверяет владение, передаёт NFT фиксированному получателю и снова проверяет владельца. Номер токена также проверяется фабрикой.
- Один активный раунд можно использовать один раз. Ранний или просроченный вызов не помечает раунд использованным. Sold-out и частичный минт — нормальные результаты с событием, без дорогого прохода по недоступным NFT. Неожиданная ошибка зависимого вызова откатывает транзакцию атомарно.

`BatchResult` позволяет отличить успешный receipt от фактического минта:

| Код | Статус | Значение |
| --- | --- | --- |
| 0 | `Minted` | Выполнен весь запрос |
| 1 | `Partial` | Выполнен доступный остаток |
| 2 | `SoldOut` | Supply закончился |
| 3 | `NotArmed` | Время старта ещё не настроено |
| 4 | `TooEarly` | Целевая секунда ещё не наступила |
| 5 | `Expired` | Целевая секунда прошла |
| 6 | `AlreadyAttempted` | Раунд уже использован |

Reader предоставляет данные о состоянии и канонической цепочке; CLI не является самостоятельным consensus-клиентом. Симуляция проверяет состояние выбранного блока, а фактический результат устанавливается только после исполнения. Один успешный локальный прогон не гарантирует попаданий в mainnet при конкуренции.

## Локальная проверка

Rust-проверки:

```bash
cargo fmt --manifest-path rust-mint-benchmark/Cargo.toml -- --check
cargo clippy --manifest-path rust-mint-benchmark/Cargo.toml --all-targets --locked -- -D warnings
cargo test --manifest-path rust-mint-benchmark/Cargo.toml --locked
cargo build --manifest-path rust-mint-benchmark/Cargo.toml --locked
```

EVM-интеграции требуют установленного Anvil. Для полного Rust CLI нужен современный Anvil с дробным `--block-time`, `--disable-min-priority-fee` и state overrides для `eth_estimateGas`; проверено с **Anvil 1.7.1**. Если `anvil` доступен в `PATH`:

```bash
node --test test/timed-benchmark-evm.test.mjs
node --test test/rust-timed-mint-evm.test.mjs
```

При нестандартной установке укажите `ANVIL_BIN`; путь к проверяемому Rust-бинарнику можно задать через `RUST_MINT_BENCHMARK_BIN`. По умолчанию интеграция использует `rust-mint-benchmark/target/debug/rust-mint-benchmark`. При отсутствии необходимых бинарников тест явно пропускается; это не считается проверенным EVM-прогоном.

Контрактные тесты проверяют 100 NFT за десять раундов, lifetime-лимит после передачи, окно времени, доступ владельца, повторы, approvals, атомарный откат при неожиданной ошибке и конкуренцию у cap: сначала 9996 реальных минта, затем внешний минт перед батчем в том же блоке, частичный результат 3 и sold-out без helpers.

Интеграция Rust CLI использует свежий Anvil без fork, синтетический ключ, 0.02 локального ETH и отдельные loopback HTTP/WS маршруты. Она выполняет реальные state-override симуляции и 26 транзакций, сверяет nonce, fee caps, `value`, события, NFT и канонические доказательства первого блока. Для полной серии проверяется путь каждого из 100 токенов через отдельный helper к получателю и `ownerOf`; helper нельзя повторно использовать для нескольких токенов. Отдельно проверяются read-only preflight, недостаточный бюджет, неверный ключ, nonce, потреблённый внешним writer, реальный timeout до принятия и потерянный ACK после принятия. Неопределённые отправки должны оставить один intent без повторной отправки, а pending-маркер должен блокировать перезапуск с новой директорией отчёта.

Финальная проверка охватывает семь сценариев Rust CLI и шесть контрактных сценариев. Обе локальные серии получили по 10 полных батчей и 10 попаданий в первый блок. После исправления сравнения канонических путей macOS отдельно повторены и пройдены оба сценария перезапуска после неопределённой отправки. Эти числа не являются mainnet-замером.
