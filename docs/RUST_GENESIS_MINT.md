# Genesis: Rust CLI с заранее созданными дочерними контрактами

**Полный public flow на сервере:** [vinos-genesis-mint](GENESIS_MINT_SERVER.md) — подготовка, ожидание реального публичного окна, финальная симуляция и отправка. В отличие от команды проверки ниже, этот запуск отправляет минт после ввода ключа.

**Проверка на сервере одной командой с вводом только приватника:** [vinos-genesis-check](GENESIS_CHECK_SERVER.md). Этот режим сам получает временный API-ключ, подготавливает двух детей и симулирует signed mint; транзакцию минта не отправляет.

`vinos-genesis` оплачивает подготовку и минт с одного кошелька. При `quantity > 1` фабрика заранее создаёт дочерние адреса. В signed-режиме каждый адрес получает собственный актуальный payload OpenSea; в public-режиме CLI строит вызов локально. Каждый ребёнок минтит один NFT и передаёт его выбранному получателю. При `quantity: 1` CLI вызывает SeaDrop прямо с кошелька.

Это одна транзакция минта за запуск. Команды подготовки могут дополнительно отправить транзакцию деплоя фабрики и транзакцию создания детей. Поддерживаются **только бесплатные минты Genesis в Robinhood mainnet, chain ID 4663**.

Текущая разработка находится в `feat/rust-signed-child-mint`; исходное состояние сохранено коммитом `59cc70a`. Старая фабрика из MJS несовместима с новой схемой. Новая фабрика имеет отдельный реестр состояния.

## 1. Сборка и конфиг

Нужен Rust **1.93 или новее**. Все команды ниже выполняются из корня репозитория:

```bash
cargo build --manifest-path rust-genesis-minter/Cargo.toml --locked --release
mkdir -p .state
cp rust-genesis-minter/config.example.json .state/genesis.config.json
```

В `.state/genesis.config.json` замени `wallet` на свой **публичный адрес**. Адрес `0x1111…1111` в примере — заглушка. По умолчанию NFT поступают на этот же кошелёк. Для другого получателя можно добавить `recipient`; при прямом минте `quantity: 1` получатель должен совпадать с `wallet`.

Короткие npm-команды доступны из того же корня: `npm run build:genesis` собирает release-бинарник; `npm run genesis -- preflight --config .state/genesis.config.json --state-dir .state/genesis-signed` запускает CLI. После `--` можно передавать любую из команд ниже и её флаги.

Приватного ключа, API-ключа и подписей в конфиге быть не должно. Неизвестные поля отклоняются. Денежные значения записываются строками, например `"0.005"` и `"10"`.

Проверка текущего состояния без отправки и без ключей:

```bash
./rust-genesis-minter/target/release/vinos-genesis preflight \
  --config .state/genesis.config.json \
  --state-dir .state/genesis-signed
```

## 2. Команды запуска

Во всех командах используй **один и тот же `--state-dir`**. Если запускаешь из другой директории, укажи абсолютные пути к конфигу и состоянию.

| Команда | Что делает |
| --- | --- |
| `preflight` | Проверяет сеть, код и разрешённые маршруты, показывает остаток, публичные окна и сохранённую фабрику. |
| `prepare --send` | Создаёт или проверяет фабрику, добавляет недостающих детей и завершает работу. Минт не запускает. |
| `setup --send` | Выполняет подготовку, затем ожидает условия старта, обновляет payload и отправляет один минт. |
| `start --send` | Использует уже сохранённую фабрику и детей; ожидает и отправляет минт. Новых контрактов не создаёт. |
| `recover` | Проверяет receipt сохранённого pending-хеша и восстанавливает учёт. Ничего не отправляет. |

### Всё одной командой: подготовить и ждать

```bash
./rust-genesis-minter/target/release/vinos-genesis setup \
  --config .state/genesis.config.json \
  --state-dir .state/genesis-signed \
  --send
```

### Сначала подготовить детей, затем запустить ожидание

```bash
./rust-genesis-minter/target/release/vinos-genesis prepare \
  --config .state/genesis.config.json \
  --state-dir .state/genesis-signed \
  --send
```

После завершения подготовки:

```bash
./rust-genesis-minter/target/release/vinos-genesis start \
  --config .state/genesis.config.json \
  --state-dir .state/genesis-signed \
  --send
```

`prepare` можно повторять: он использует существующую фабрику и добавляет только недостающее число неиспользованных детей. После израсходования детей следующая команда `start` может потребовать новый `prepare`.

### Проверить без отправки

Убери `--send` из `prepare`, `setup` или `start`. Команда ничего не отправит. Если фабрика или дети ещё не существуют, dry-run покажет ближайший шаг подготовки и завершится: полного минта через несуществующие контракты этот режим не симулирует. С уже подготовленной фабрикой `start` выполняет ожидание и финальную симуляцию, затем завершается без отправки.

Для `preflight` и `recover` флаг `--send` запрещён.

## 3. Как вводить ключи

Команды с `--send` показывают скрытый запрос:

```text
Private key (hidden, never saved):
```

Вводи приватный ключ непосредственно в этот терминал и нажимай Enter. Символы не отображаются. CLI проверяет, что ключ соответствует `wallet`. Ключ не передаётся аргументом команды и не сохраняется в файлы состояния.

Для `setup` и `start` в режимах `auto` и `signed` дополнительно появится:

```text
OpenSea API key (hidden, never saved):
```

Это API-ключ OpenSea, а не подпись кошелька. Он нужен и для dry-run, если выбран `auto` или `signed`. В `public` API-ключ не требуется. `prepare` запрашивает только приватный ключ при `--send`; `preflight` и `recover` ключей не запрашивают.

Ввод через stdin и подмена API предусмотрены только для изолированных локальных тестов; обычный запуск использует скрытые терминальные запросы.

## 4. Количество, режим и ожидание

```json
{
  "quantity": 10,
  "minQuantity": 1,
  "mode": "auto"
}
```

- `quantity`: желаемый максимум, от 1 до 100. CLI ограничивает подготовку и батч доступным количеством.
- `minQuantity`: минимум для подготовки и финальной симуляции. При `1` допускается частичный результат.
- `auto`: выбирает активный бесплатный public-этап; иначе обращается к OpenSea за payload для каждого minter.
- `public`: ожидает бесплатный публичный этап, подписей OpenSea не использует.
- `signed`: принимает только `mintSigned`, отдельно проверяя разрешение каждого адреса.

Флаг `--quantity N` переопределяет максимум из конфига на один запуск. Остальные ограничения, включая `minQuantity`, сохраняются и проверяются повторно. Например, при `minQuantity: 1` флаг `--quantity 1` выбирает прямой минт без подготовки фабрики или детей.

**`minQuantity` не откатывает уже выполненные минты.** Если в симуляции было десять, а к исполнению осталось три, фабрика сохраняет три успешных NFT. При результате ниже минимума `setup`/`start` возвращает код выхода `2`; успешные NFT и потраченный газ остаются учтены. Код `0` означает, что минимум достигнут, `1` — остановку из-за ошибки.

Фабрика читает текущий выпуск перед каждым ребёнком. У signed-этапа дополнительно учитывается `maxTokenSupplyForStage`. Ошибка отдельного ребёнка откатывает его собственный минт и перевод, сохраняя предыдущие успехи. Три подряд неудачных дочерних вызова завершают батч; успешный вызов сбрасывает этот счётчик. Всего одна фабрика может создать до 1024 детей.

Чтобы разрешить отправку не раньше определённого времени или блока, добавь:

```json
{
  "waitUntilTimestamp": 1800000000,
  "waitUntilBlock": 70000000
}
```

Это примеры, а не расписание Genesis. `waitUntilTimestamp` — Unix timestamp в секундах. Проверяется **время блока сети**, не локальные часы компьютера. Если заданы оба поля, должны выполниться оба условия, а также условия самого минта. Без этих полей процесс ждёт доступного этапа. `waitTimeoutSecs` ограничивает ожидание; по умолчанию это 86400 секунд, допустимый максимум — 172800 секунд (48 часов).

Для быстрого обнаружения изменений можно включить отдельную подписку на логи:

```json
{
  "watchRpc": "wss://robinhood-rpc.publicnode.com",
  "pollIntervalMs": 250
}
```

Это читающий WebSocket RPC, не sequencer feed и не адрес отправки. Подписка получает события только Genesis и его заранее одобренных SeaDrop. Событие будит проверку состояния; данные события не задают nonce, доверенный номер блока или разрешение на отправку. Новый неизвестный SeaDrop автоматически не принимается.

При работающей подписке пауза между резервными опросами далёкого public-stage достигает 10 секунд; событие прерывает её. Без `watchRpc` либо после отказа подписки пауза — не более секунды. В последние 30 секунд применяется `pollIntervalMs`. Время RPC добавляется к этим паузам; поток событий объединяется с ограничением четыре начала снимка в секунду. Это не гарантия обнаружения за 250 мс: провайдер тоже может задержать уведомление. Три последовательных сбоя WSS отключают подписку с событием `drop_watch` / `degraded`, оставляя опросы. Ошибки транспорта читающего RPC во время ожидания дают до трёх попыток переподключения, затем процесс останавливается; ошибки идентичности и формата не повторяются.

`drop_state_changed` показывает прежние и новые параметры: разрешённые SeaDrop, цену, начало/конец, лимит адреса, разрешение настроенного fee recipient, fee BPS и supply. Изменение условий удаляет подготовку; обычное уменьшение остатка конкурентами не заставляет бесконечно пересобирать батч. Подготовка детей не отправляется, если среди проверенных маршрутов нет бесплатного разрешённого публичного окна сейчас или в будущем.

После финального `eth_call` бот ещё раз читает текущие условия и проверяет разрешения подписантов для signed-payload. Изменение правил отменяет отправку и запускает новую подготовку. Смена номера блока сама по себе не отменяет транзакцию. `mint_preflight` содержит `simulationBlock`, `policyCheckedBlock`, `finalPreflightMs`; дополнительные RPC-чтения входят в `maxPreflightAgeMs`. После трёх превышений срока актуальности подготовки процесс останавливается. Ошибка транспорта внутри финальной проверки может остановить его сразу; автоматическое восстановление читателя ограничено циклом ожидания. Эти чтения не расходуют газ, но добавляют задержку. Изменения после последней проверки и до включения всё ещё возможны; финальная симуляция не резервирует supply и не отменяет уже отправленную транзакцию.

Проверка соединения с секвенсором выполняется во время ожидания примерно раз в 10 секунд. Она ограничена тремя попытками: после обычной RPC-ошибки клиент переиспользуется, после ошибки транспорта создаётся новое соединение. После потери всех отправляющих endpoints процесс останавливается. Это проверка доступности, не повтор отправки транзакции. Ошибка идентичности сети не считается временной.

## 5. Изменения подписей, этапа и контракта

В конфиге предусмотрены отдельные интервалы:

| Поле | Пример | Назначение |
| --- | --- | --- |
| `pollIntervalMs` | 1000 | Пауза между циклами проверки состояния сети. |
| `payloadRefreshMs` | 5000 | Интервал обновления подготовленной партии payload. |
| `maxPayloadAgeMs` | 15000 | Предельный возраст payload, считая с начала запроса. |
| `maxPreflightAgeMs` | 2000 | Максимальное время от начала финальной проверки до отправки. |
| `minSignatureRemainingSecs` | 5 | Минимальный остаток срока signed-этапа по времени блока. |

Полное обновление занимает ещё и время сетевых запросов. Для десяти детей API получает десять запросов с ограничением `concurrency`; интервал 5 секунд не гарантирует, что вся партия будет получена за 5 секунд. HTTP-клиенты переиспользуются. Соединения отправки проверяются заранее и во время ожидания.

Если нужно обновлять payload чаще, можно уменьшить `payloadRefreshMs` до `1000`, учитывая квоту API. Ответ `429` учитывает `Retry-After`; три последовательных учитываемых ошибки API останавливают процесс. Состояние «этап ещё не активен» обрабатывается как ожидание. Три последовательных срыва финальной подготовки также останавливают запуск. Неизвестный контракт или недопустимый payload прекращают работу сразу.

Перед подписью транзакции CLI проверяет актуальные права подписанта, лимиты и срок каждого payload, получает комиссию и nonce, затем выполняет точный `eth_call` всей транзакции с выбранным gas limit. Если подготовка успела устареть, она не отправляется. Изменение состояния после последней проверки всё ещё может повлиять на исполнение; дочерние ошибки изолируются фабрикой.

### Что происходит при смене адресов

`routes` — список заранее проверенных SeaDrop-маршрутов. Для каждого заданы адрес, Keccak-256 runtime-кода и получатель комиссии. Маршрут должен одновременно находиться в разрешённом списке Genesis. Payload с неизвестным адресом не исполняется: сначала нужно исследовать новый контракт и обновить разрешённый маршрут в конфиге.

Смена SeaDrop внутри проверенных маршрутов не требует пересоздания детей. NFT и получатель зафиксированы в фабрике. Production-режим этого CLI допускает только исследованный Genesis с указанным хешем кода; произвольная замена `nft` в конфиге не поддерживается.

### Главное ограничение signed-режима

Используется [официальный метод OpenSea для построения транзакции минта](https://docs.opensea.io/reference/build_drop_mint_transaction): запрос идёт отдельно для каждого дочернего `minter`. Подпись основного кошелька не подходит другим адресам.

**Выдача настоящих Genesis-разрешений дочерним адресам пока не подтверждена.** Если адрес не имеет права на этап, API может отказать. Код не создаёт это право и не обходит проверку подписанта. Деплой фабрики и детей может потратить газ до такого отказа; потраченный газ подготовки не возвращается.

## 6. Газ и денежные пределы

Пример рассчитан на отдельный бюджет до `0.019 ETH` с резервом `0.001 ETH`:

| Поле | Значение | Что ограничивает |
| --- | --- | --- |
| `maxGasCostEth` | `"0.005"` | Максимальную оценку расходов одной транзакции. |
| `maxTotalGasCostEth` | `"0.019"` | Уже учтённые расходы в этом state плюс максимум следующей транзакции. |
| `reserveEth` | `"0.001"` | Баланс, который должен остаться сверх максимума следующей транзакции. |
| `maxFeePerGasGwei` | `"10"` | Верхнюю цену единицы газа в подписываемой транзакции. |
| `maxPriorityFeePerGasGwei` | `"0"` | Заданную priority fee. |
| `maxFeeMultiplier` | `4` | Запас к текущей базовой/рекомендованной цене, ограниченный верхней ценой. |
| `gasPerChild` | `1000000` | Предел газа одного дочернего вызова. |

Срабатывают все пределы одновременно. Больший баланс кошелька сам по себе их не увеличивает. Если рассчитанная транзакция не помещается, CLI останавливается с `GAS_BUDGET_EXCEEDED`, `BASE_FEE_EXCEEDS_CONFIGURED_GAS_PRICE` или `BALANCE_CANNOT_COVER_GAS_AND_RESERVE`.

```text
Максимум расходов = gasLimit × maxFeePerGas
Учтённая фактическая комиссия = gasUsed × effectiveGasPrice из receipt
```

При `quantity: 10` и `gasPerChild: 1000000` минимальный gas limit батча составляет **11 138 730** единиц, включая запас фабрики. Например, при цене **0.1 gwei** это максимум **0.001113873 ETH**, при **1 gwei** — **0.01113873 ETH**. Это арифметические примеры, не текущая цена сети; второй вариант превышает примерный лимит одной транзакции `0.005 ETH`.

Зарезервированный газ не означает, что он весь будет израсходован. Фактические затраты зависят от успешно выполненных и неудачных вызовов. Газ деплоя и создания детей оплачивается отдельно и входит в общий учёт. Для батча CLI использует консервативный минимум газа, потому что обычный `eth_estimateGas` может найти дешёвый путь с нулём минтов. После выбора лимита обязательна точная симуляция.

## 7. Состояние и восстановление

При стандартных путях файлы находятся здесь:

```text
.state/genesis-signed/4663-<адрес кошелька>/state.json
.state/genesis-signed/4663-<адрес кошелька>/wallet.lock
.state/genesis-signed/4663-<адрес кошелька>/events.jsonl
```

Сохраняются идентификаторы сети, кошелька, NFT, получателя и артефакта; адрес фабрики; pending-хеш и параметры намерения; уже учтённый газ. Приватный ключ, API-ключ, mint payload и подписанная raw-транзакция не сохраняются. Запись состояния атомарная; локальная блокировка защищает один каталог от двух одновременных процессов. Разные каталоги на разных серверах общей блокировки не имеют.

Каталог конкретного кошелька создаётся с правами `700`, файлы — `600`. На Unix CLI отклоняет каталог кошелька с доступом группы или остальных пользователей: `STATE_DIRECTORY_MUST_BE_PRIVATE_CHMOD_700`. После переноса состояния сохрани эти права. Символические ссылки в пути состояния не допускаются.

Если отправка дала timeout, это ещё не означает, что транзакция не принята. CLI проверяет receipt того же хеша. При неопределённом результате состояние остаётся pending, новый минт или деплой не запускается автоматически.

```bash
./rust-genesis-minter/target/release/vinos-genesis recover \
  --config .state/genesis.config.json \
  --state-dir .state/genesis-signed
```

`recover` проверяет receipt без длительного ожидания; если его ещё нет, завершится ошибкой о неразрешённой транзакции. Повтори проверку после появления receipt. Восстановление выполняется до запросов ключей и проверки текущего этапа: перенос минта или смена разрешённого SeaDrop не мешают проверить уже завершённую транзакцию. Повторный `setup`/`start`, обнаружив завершённый pending-минт, восстанавливает именно его результат и завершает работу без новой отправки.

Receipt проверяется по хешу транзакции, отправителю, назначению, логам и соответствию каноническому блоку RPC. Это проверка включения в наблюдаемую L2-цепочку, не ожидание окончательной финальности на L1.

Не удаляй state для обхода ошибки pending или несовпадения идентичности. Изменение владельца, получателя, NFT или артефакта требует отдельного разбора; автоматического создания ещё одной фабрики в такой ситуации нет.

## 8. HTTPS, WSS и вывод задержек

По умолчанию отправка идёт на официальный HTTPS endpoint:

```text
https://sequencer.mainnet.chain.robinhood.com
```

`sendRpcUrls` допускает несколько HTTPS/WSS JSON-RPC endpoints. CLI параллельно рассылает **одну и ту же подписанную транзакцию**, ограничивая число одновременных запросов через `concurrency`. Это один nonce и один hash, а не несколько независимых минтов.

WSS публичного RPC-провайдера — подключение к провайдеру. Прямая отправка по WSS на публичный адрес официального секвенсора в предыдущих проверках не подтверждена: Upgrade отклонялся. `wss://feed.mainnet.chain.robinhood.com` служит для получения данных; в `sendRpcUrls` его ставить нельзя. [Официальные адреса Robinhood](https://docs.robinhood.com/chain/connecting/).

Вывод состоит из JSON-событий: `preflight`, `children_ready`, `payloads_ready`, `waiting`, `mint_preflight`, `rpc_ack`, `mint_result`. `rpc_ack.roundTripMs` измеряет запрос отправки до ответа RPC. `submission_complete.receiptObservedMs` — время до наблюдения receipt через read RPC. Ни одно из этих значений само по себе не доказывает первое место в блоке.

## 9. Проверки и подтверждённые границы

Полный локальный набор, включая сборку debug-бинарника и EVM-тесты:

```bash
npm ci
npm run test:genesis
```

Нужны Node.js 18.18+, Rust и Anvil. Отдельные команды:

```bash
cargo test --manifest-path rust-genesis-minter/Cargo.toml --locked
node --test test/genesis-child-evm.test.mjs test/rust-genesis-minter-evm.test.mjs
```

Перед Node EVM-тестами нужен Anvil и собранный debug-бинарник:

```bash
cargo build --manifest-path rust-genesis-minter/Cargo.toml --locked
```

Для пересборки Solidity-артефакта используется закреплённый `solc 0.8.26` из Node-зависимостей:

```bash
node scripts/compile-genesis-child.mjs
```

Итоговый локальный набор: **25 Rust-тестов, 11 EVM-тестов контрактов и 10 CLI EVM-тестов прошли**. Проверены public/signed батчи, отдельная подпись каждого ребёнка, гонка за остаток, частичный успех, остановка после трёх ошибок, защита от reentrancy, переиспользование состояния и восстановление после потери ACK. Дополнительные регрессии проверяют некорректный `uint256` в ответе RPC, истечение срока финальной проверки и устаревший payload: во всех трёх случаях отправок нет.

На локальном форке **настоящего Genesis подтверждён один минт через заранее развёрнутого ребёнка с переводом NFT получателю**. Для этой ветки Genesis нужен Cancun: safe-receiver путь исполняет `MCOPY`. Полный fork-батч из десяти не подтверждён: PublicNode отказал в чтении части исторического storage без персонального токена. Opt-in тест различает этот отказ и ошибку контракта:

```bash
GENESIS_FORK_RPC=https://robinhood-rpc.publicnode.com \
  node --test test/genesis-child-fork.test.mjs
```

В этой доработке mainnet-транзакции не отправлялись. Проверка реальной выдачи OpenSea-подписей детям остаётся отдельным необходимым шагом перед signed-минтом.
