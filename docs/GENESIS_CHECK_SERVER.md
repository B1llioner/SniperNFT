# Проверка Genesis на EC2 одной командой

Команда `vinos-genesis-check` предназначена для проверки **двух дочерних адресов**, которым OpenSea должен разрешить signed mint. Она получает временный API-ключ сама; пользователь вводит только приватный ключ кошелька `0x59Cd658EB1be492c52CcAA2575A90A236F77fAE2`.

## Запуск после установки на сервер

На выбранном EC2, в интерактивной SSM-сессии под `ssm-user`:

```bash
vinos-genesis-check
```

Вводить ключ следует только после строки:

```text
Private key (hidden, never saved):
```

Ключ скрыт при вводе, не передаётся в аргументах команды и не записывается в конфиг, state или логи. Launcher отключает core dumps и запускает процесс с очищенным окружением. Не вставляй ключ в команду, чат или CloudShell, если там ещё не открыт нужный скрытый запрос.

Из [CloudShell Ohio](https://us-east-2.console.aws.amazon.com/cloudshell/home?region=us-east-2) подключение и запуск можно объединить:

```bash
aws ssm start-session --region us-east-2 --target i-0ef42c1e5475d7edb --document-name AWS-StartInteractiveCommand --parameters '{"command":["/usr/local/bin/vinos-genesis-check"]}'
```

Эта команда требует уже установленного launcher и доступа к документу интерактивной сессии. Параметры `start-session` описаны в [документации AWS](https://docs.aws.amazon.com/cli/latest/reference/ssm/start-session.html). До фактической установки команда на EC2 отсутствует; наличие этого документа само по себе не означает, что установка уже выполнена.

## Что проверяется

1. Сеть 4663, runtime Genesis и SeaDrop, разрешённый маршрут, остаток и сохранённая фабрика.
2. Доступность [автоматической выдачи API-ключа OpenSea](https://docs.opensea.io/reference/api-keys), срок и опубликованные лимиты. Ошибка на этом шаге останавливает процесс до запроса приватника и платной подготовки.
3. Соответствие приватника заданному публичному адресу, RPC отправки, nonce, цена газа, баланс и денежные пределы.
4. Фабрика и два неиспользованных ребёнка. Существующая фабрика используется повторно; недостающее создаётся. **Это реальные транзакции подготовки с оплатой газа.**
5. По одному запросу OpenSea для каждого ребёнка. Всего одна партия из двух запросов, без автоматической смены API-ключей или повторного опроса этапа.
6. Привязка подписи к ребёнку, актуальный подписант, сроки и ограничения, затем симуляция обоих минтов и переводов через фабрику с итоговым лимитом газа.

**Транзакция минта никогда не отправляется этим launcher.** Даже внутренний флаг `--send` относится только к подготовке. Успешная проверка оставляет обоих детей неиспользованными.

Проверка относится к прочитанному состоянию сети. Она не резервирует NFT и не гарантирует будущую доступность после изменения этапа.

## Как выглядит результат

Успех содержит событие:

```json
{"event":"child_check_result","passed":true,"mintSent":false,"simulatedMintCount":2}
```

Также выводятся адрес фабрики, оба дочерних адреса и накопленная фактическая стоимость подготовки. Строка `CHECK PASSED` появляется только после получения и проверки обоих разрешений и успешной симуляции.

Возможные остановки:

- `409` / `stage_not_active`: этап сейчас не активен; допуск детей не проверен.
- `422` / `mint preconditions failed`: возможны ограничения участия, баланс minter, лимит или остаток. Это не доказательство общего запрета контрактов.
- `API_RETURNED_DIFFERENT_STAGE_MODE`: OpenSea выбрал public/другой маршрут; signed-допуск не подтверждён.
- `429`: ограничение запросов; новая учётная запись/ключ для обхода лимита автоматически не создаётся.
- Ошибка подписи, срока, симуляции или бюджета: проверка не пройдена, минт не отправлен.
- `PENDING_MINT_RECOVERED_CHILD_CHECK_NOT_PERFORMED_RERUN_CHECK`: восстановлен ранее отправленный минт; данная проверка не выполнялась. Это отдельная остановка с ненулевым кодом выхода.

Не считать один код выхода 0 от других команд доказательством допуска: нужна именно успешная запись `child_check_result` текущего запуска.

## Файлы и бюджет

Launcher: `/usr/local/bin/vinos-genesis-check`.

Версия бинарника и фиксированный конфиг: `/opt/vinos-genesis/<SHA256 архива>/`.

Состояние и события: `/var/lib/vinos-genesis/4663-<адрес>/state.json` и `events.jsonl`. Каталоги принадлежат `ssm-user` и закрыты правами 0700. Не удалять state после ошибки отправки: pending-хеш нужен для восстановления без повторного деплоя.

В конфиге: максимум `0.005 ETH` на транзакцию, `0.019 ETH` накопленного газа, резерв `0.001 ETH`. Это верхние пределы допуска к отправке; фактическая стоимость берётся из receipts. Отказ OpenSea после подготовки не возвращает уже потраченный газ.

## Подготовка пакета и установка

Для разработчика, после тестов и ревью:

```bash
node scripts/package-genesis-check.mjs --output-dir .state/genesis-check-kit-01
```

Пакет содержит только разрешённые исходники, lockfiles, артефакты и установщик. Конфиги с секретами, содержимое `.state` и кошельки в него не входят. SHA256 каждого исходника и архива фиксируются в manifest.

В CloudShell установщик собирает Linux x86_64 release-бинарник закреплённым Rust 1.93.0, проверяет исходники/ELF/checksums, доставляет его через существующий закрытый S3-бакет и SSM только на выбранный EC2. Установка не запрашивает приватник и не отправляет blockchain-транзакций. Существующий `vinos-real-tx` остаётся отдельной командой платного бенчмарка.

Конкретные команды сборки и SHA256 находятся в созданном `kit-manifest.json`; команды установщика перечисляет `bash install-genesis-check.sh --help`. Не повторять неопределённый `send-command` вслепую: сначала проверить записанный command ID/intent.
