# Сравнение площадок по задержкам до sequencer

`benchmark:az` измеряет путь до одного endpoint с разных серверов и сравнивает сохранённые отчёты. Кошелёк, ETH и приватный ключ для него не нужны. Отправляются только запросы `arb_checkPublisherHealth` и, при явном `--ec2`, читаются поля размещения инстанса через IMDSv2.

## Три одинаковых сервера в Ohio

Готовы CloudFormation-шаблон и [порядок развёртывания в AWS](AWS_AZ_BENCHMARK.md): три одинаковых EC2, по одному в `use2-az1`, `use2-az2`, `use2-az3`. Зоны заданы через Zone ID. Имена вида `us-east-2a` могут обозначать разные физические зоны у разных AWS-аккаунтов; Zone ID стабилен между аккаунтами. [Документация AWS](https://docs.aws.amazon.com/ram/latest/userguide/working-with-az-ids.html).

Сохранить шаблон для просмотра и дальнейшего запуска:

```bash
npm run benchmark:az -- aws-template --output ohio-template.json
```

Эта команда только записывает локальный файл. Создание и удаление ресурсов выполняются отдельными AWS CLI-командами из инструкции.

Подготовить пакет для серверов:

```bash
npm run benchmark:az -- bundle --output az-benchmark.tgz
```

Архив содержит CLI, его библиотеки, документацию и шаблон AWS. В нём нет приватных конфигов, `.env`, ключей, `node_modules` или отправителя реальных транзакций. Команда печатает SHA-256 архива. Для пакета достаточно Node.js; устанавливать npm-зависимости не требуется.

## Запуск измерения

На каждом сервере из каталога проекта или распакованного пакета:

```bash
node az-benchmark.mjs probe --label ohio-1 --ec2 --duration-seconds 1800 --output ohio-1.json
```

На втором и третьем сервере поменяйте `--label` и имя файла на `ohio-2`, `ohio-3`. При наличии полного проекта можно использовать префикс `npm run benchmark:az --` вместо `node az-benchmark.mjs`.

`--ec2` получает через IMDSv2 только регион, имя зоны, Zone ID и тип инстанса. Данные IAM-роли и ключи не читаются. На другом VPS уберите `--ec2`; при необходимости укажите `--zone-id`, `--zone-name`, `--region` вручную. Источник метаданных сохраняется в отчёте.

### Общий старт по UTC

Выберите одно время на несколько минут вперёд. На всех трёх серверах передайте **одинаковое значение**, заменив обозначение времени:

```bash
node az-benchmark.mjs probe --label ohio-1 --ec2 --start-at YYYY-MM-DDTHH:mm:ssZ --duration-seconds 1800 --output ohio-1.json
```

В AWS-инструкции есть команда получения такого времени. Часы серверов должны быть синхронизированы: CLI не измеряет смещение часов между машинами. Во время подготовки выполняется прогрев, затем поддерживается соединение до общего старта. Прогрев не входит в выборку. Если указанное время прошло до завершения подготовки, скрипт остановится и потребует более поздний старт.

В отчёт попадают начало и конец измерения, каждая отдельная проба, IP ответившего endpoint, тип соединения, Node/ОС/CPU, задержки event loop и изменение локальных часов. IP может различаться между зонами или меняться по DNS: одинаковый URL не гарантирует одинаковый физический backend. Имя или AWS-зона самого sequencer из этих данных не выводятся.

## Что измеряется

Обычный режим длится 30 минут:

- Раз в секунду — health-запрос через сохраняемое HTTPS-соединение.
- Раз в 30 секунд — отдельный запрос с новым TCP/TLS-соединением, без возобновления TLS-сессии.
- Раз в 30 секунд — промежуточные p50/p95/p99 и сохранение отчёта.

Не более одного незавершённого запроса каждого вида. Запоздавшие интервалы пропускаются и считаются отдельно, без серии догоняющих запросов. Таймаут одного запроса — 5 секунд. Перенаправлений и автоматических повторов нет.

| Группа | Смысл |
| --- | --- |
| `warmReused` | Запрос действительно использовал уже открытый TCP/TLS socket |
| `warmReconnect` | Запрос из обычной серии потребовал нового соединения |
| `cold` | Отдельная проба с намеренно новым соединением |

Для групп доступны p50/p95/p99/min/max и размах `p99 − p50`. Метрики `dns`, `tcp`, `tls` показывают длительность соответствующего этапа, когда он выполнялся. `firstByte` и `total` считаются от начала вызова запроса и включают подключение, если оно потребовалось. На повторно используемом socket DNS/TCP/TLS отсутствуют, а не подменяются нулями.

Ошибки, HTTP 429, таймауты, переподключения и смены IP выводятся отдельно. Процентили задержек считаются только по успешным ответам, поэтому сравнение дополнительно проверяет долю ошибок и полноту измерений.

Health RTT измеряет запрос и ответ сервера. TCP/TLS/health не являются временем поступления транзакции к sequencer, включением в блок или финальностью. Для реальной отправки есть отдельный второй этап ниже.

## Сравнение отчётов

Скопируйте три JSON-файла на одну машину:

```bash
npm run benchmark:az -- compare ohio-1.json ohio-2.json ohio-3.json --output ohio-comparison.json
```

CLI пересчитывает статистику из исходных проб в **общем временном окне**. Сохранённым готовым p95 из файла он не доверяет. Разный endpoint, IP family, протокол, метод или настройки измерения дают отказ от сравнения.

Условный кандидат по задержке выбирается по `warmReused total p95`, затем p99 и p50. Для ранжирования все отчёты должны пройти проверки:

- Прогоны завершены; общее окно покрывает не меньше 80% запрошенной длительности.
- Есть не менее 100 успешных проб с повторно использованным socket в каждом отчёте.
- Выполнено не меньше 80% ожидаемых обычных проб в общем окне.
- Доля ошибок обычной серии не выше 1%, доля успешных запросов на повторно использованном соединении не ниже 95%.
- Если записан тип EC2-инстанса, он не должен отличаться между сравниваемыми площадками.

Если условий недостаточно, таблица остаётся доступной, но победитель не назначается; команда завершится с кодом `2`. Повреждённые или несовместимые отчёты дают код `1`. Даже при подходящих данных результат обозначен как предварительный кандидат по этому замеру. Это не гарантия победы в гонке транзакций. Для p99 полезны более длинные повторные серии; одна выборка не устанавливает стабильный сетевой рекорд.

## Настройки

Полный пример: [az-benchmark.config.example.json](az-benchmark.config.example.json).

```bash
npm run benchmark:az -- probe --label ohio-1 --ec2 --config az-benchmark.config.example.json --output ohio-1.json
```

| Флаг | Значение по умолчанию | Диапазон |
| --- | --- | --- |
| `--duration-seconds` | 1800 | 1–7200 |
| `--interval-ms` | 1000 | 250–60000 |
| `--cold-interval-ms` | 30000 | 5000–300000 |
| `--timeout-ms` | 5000 | 100–20000 |
| `--family` | 4 | 4, 6 либо 0 — выбор системы |
| `--connect-ip` | DNS | IPv4 из текущего DNS для сравнения клиентов на одном адресе; Host, SNI и проверка TLS сохраняются |
| `--warmup-samples` | 5 | 0–20 |
| `--progress-interval-seconds` | 30 | 1–300 |

Для одинакового теста сохраняйте одинаковые настройки. В шаблоне AWS используется IPv4. Уменьшение интервалов увеличивает нагрузку на endpoint и может менять результат из-за ограничения частоты запросов. Публичные endpoints Robinhood имеют rate limits. [Официальные адреса и ограничения](https://docs.robinhood.com/chain/connecting/).

Endpoint по умолчанию: `https://sequencer.mainnet.chain.robinhood.com`. Feed `wss://feed.mainnet.chain.robinhood.com` для этого измерения не используется. Для своего send endpoint есть `--endpoint`; полный URL с возможным API-токеном не записывается в отчёт, сохраняются только origin и SHA-256 нормализованного URL для проверки совпадения.

Файлы создаются с правами `0600`, существующие отчёты не перезаписываются. Во время прогона обновляется только принадлежащий ему файл, через замену готового временного JSON. `Ctrl+C` сохраняет частичные наблюдения с `completed: false`. Их можно просмотреть и сравнить по цифрам, но ранжирование неполного прогона не выполняется.

## Второй этап: реальная отправка

Для сравнения Node и Rust можно закрепить одинаковый актуальный IPv4 через `--connect-ip`.
Фактический адрес сохраняется в каждой пробе; сравнение отклоняет отчёты с разными pin-настройками.
Закрепление IP убирает выбор разных DNS-адресов, но не гарантирует один процесс за балансировщиком.
Не сохраняйте IP навсегда в рабочем конфиге: адреса сервиса могут измениться.

Для площадок с лучшими результатами установите полный проект и используйте ранее созданную команду:

```bash
npm run benchmark:sequencer -- --cycles 100 --send
```

Она делает до 200 транзакций: каждый цикл разворачивает отдельный тестовый NFT-контракт, затем вызывает mint. Нужен отдельный оплачивающий кошелёк на каждой одновременно работающей машине, чтобы разные отправители не конкурировали за nonce. Держите одинаковые параметры, read RPC и время теста. Инструкции по скрытому вводу ключа, общему бюджету и p95/p99: [SEQUENCER_BENCHMARK.md](SEQUENCER_BENCHMARK.md).

Сравнивайте ответ sequencer и обнаружение receipt отдельно. Быстрый health сам по себе не доказывает быструю реальную отправку. `compare` этой команды принимает только отчёты первого, сетевого этапа; JSONL с транзакциями имеет другой формат.

## Проверки

`npm test` проверяет локальные HTTP/HTTPS fixtures, реальное переиспользование socket, полный TLS handshake, таймауты, ошибки, отмену, CLI и сравнение синтетических отчётов. Инфраструктурный шаблон проверяется структурными тестами; он также проверен `cfn-lint`. Локальные проверки не создают EC2 и не измеряют задержки AWS до mainnet.
