# Ревью: Genesis mint через заранее созданных детей

Дата: 16 сентября 2026. База — `59cc70a`, ветка — `feat/rust-signed-child-mint`.

## Результат и область проверки

Добавлены отдельный Rust CLI, новая фабрика и адаптер ребёнка. Старые MJS-команды и Rust-бенчмарки сохранены. Выполнены независимое ревью Solidity и ревью Rust-оркестрации, локальные EVM-тесты и тесты настоящего CLI. Выявленные ниже ошибки исправлены; известных блокирующих дефектов в проверенной области не осталось. Это внутреннее ревью реализации, а не независимый внешний аудит.

**Успешный signed mint настоящего Genesis через OpenSea пока не подтверждён.** Локальный API выдавал тестовые подписи. Реальный backend может отказать дочерним адресам из-за правил этапа, лимитов или проверки баланса. Деплой до этого отказа расходует газ.

## Архитектура и доверие

```text
EOA → prepare: фабрика → заранее развёрнутые дети
                   ↓
Rust → OpenSea: отдельный запрос {minter: child, quantity: 1}
                   ↓
ABI / EIP-712 / runtime / текущие ограничения / точный eth_call
                   ↓
EOA → одна mintBatch-транзакция → дети → SeaDrop → Genesis
                                      └─ NFT → неизменяемый recipient
```

- Владелец фабрики — единственный отправитель, имеющий право создавать детей и запускать батч. Получатель и NFT неизменяемы.
- Ребёнок принимает mint-вызов только от своей фабрики. Callback ERC721 разрешён только от NFT, при активном минте ожидаемого ID и `from == 0`.
- Genesis определяет выпуск и разрешённые SeaDrop; SeaDrop проверяет подпись, одноразовость и допуск minter. Самостоятельно выпустить разрешение OpenSea фабрика не может.
- Rust не доверяет целям из API. Проверяются chain ID, NFT, проверенный SeaDrop, fee recipient, minter, quantity, нулевая цена, каноническая ABI-кодировка и подпись. На этапе исполнения контракт также ограничивает доступные вызовы.
- Production ограничен исследованным runtime Genesis. Подмена коллекции требует нового исследования и разработки. Проверенный новый SeaDrop можно добавить в конфиг; NFT должен разрешать его на сети.
- RPC необходим для достоверного состояния, nonce, стоимости и receipt. Проверка хеша блока receipt выявляет несогласованность ответа, но не доказывает финальность на L1 и не устраняет доверие к read RPC.

Основание для интеграции: [API OpenSea](https://docs.opensea.io/reference/build_drop_mint_transaction), [официальный SDK](https://github.com/ProjectOpenSea/opensea-js/blob/main/src/api/drops.ts), [SeaDrop](https://github.com/ProjectOpenSea/seadrop/blob/main/src/SeaDrop.sol), [предыдущий анализ Genesis](OPENSEA_FRESHNESS_REVIEW.md).

## Инварианты

1. Один успешно использованный ребёнок больше не минтит. Payload можно заменить до его успешного использования без пересоздания ребёнка.
2. Каждый mint бесплатный и получает ровно один NFT. Нет переводов ETH, approvals, delegatecall или произвольного назначения calldata.
3. До каждого ребёнка читается текущий остаток. Конкурирующая транзакция, исполненная раньше, уменьшает фактический результат; между шагами одной EVM-транзакции другая транзакция не вклинивается.
4. Ошибка ребёнка откатывает только его вызов. Три последовательные ошибки останавливают цикл, успешный вызов сбрасывает счётчик. После первого успеха нет проверки минимального результата, откатывающей весь батч.
5. Вызовы детей ограничены газом; фабрика сохраняет запас на завершение и копирует ограниченный объём returndata. Глобальные ошибки входных аргументов проверяются до первого минта.
6. `minQuantity` ограничивает предварительный допуск к отправке. Если гонка оставила меньше, успешные NFT сохраняются, результат отражается в receipt и коде выхода.
7. Все endpoints получают одну подписанную транзакцию с одним hash/nonce. Неопределённый результат не вызывает автоматическую замену, новый nonce или повторный деплой.
8. Intent записывается на диск до первого возможного вызова отправки. Реестр привязан к сети, EOA, NFT, recipient и артефакту; незавершённый intent сверяется с receipt до продолжения работы.
9. Возраст payload и финальной проверки проверяется после симуляции, подписи и дисковой записи, а также перед каждым запросом отправки, ожидавшим своей очереди.
10. Цена газа, лимит газа, максимум стоимости транзакции, накопленные расходы и резерв проверяются до подписи. Учитываются receipt `gasUsed × effectiveGasPrice`, включая reverted-транзакции.

## Найденные и исправленные ошибки

| Проблема | Исправление | Подтверждение |
| --- | --- | --- |
| Payload мог устареть во время финальной симуляции, а дисковая запись — задержать отправку после проверки срока | Единый deadline — минимум возраста всех payload и финальной проверки; проверки непосредственно перед отправкой | Два CLI-теста задерживают успешный `eth_call`: после трёх срывов подготовки — ноль отправок |
| После принятого минта и потери ACK повторный `start` мог восстановить receipt, затем начать ещё один минт | Восстановленный pending mint завершает запуск со своим сохранённым результатом | CLI: подготовлено 20 детей, сминчено 10, ACK потерян; перезапуск не использует оставшихся детей |
| Преобразование недоверенного результата RPC из U256 в u64 могло вызвать panic | Значение ограничивается размером батча до преобразования | RPC возвращает `2^64`: контролируемая ошибка, ноль отправок |
| `eth_estimateGas` может оценить дешёвый путь фабрики, который завершится без минтов | Минимальный gas limit из числа детей и лимита дочернего вызова; обязательный точный `eth_call` с итоговым газом | Rust-проверка формулы, CLI успешного батча, контрактный тест малого остатка газа |
| Восстановление могло зависеть от текущего этапа и повторного ввода ключей | Pending mint обрабатывается до API, скрытого ввода и чтения текущих маршрутов | CLI восстановления и независимое ревью |
| Receipt мог быть записан как завершённый до проверки получения NFT | До очистки pending проверяются отправитель, назначение, стоимость, блок, NFT-события и BatchResult | CLI полного signed-маршрута и восстановления |
| Некорректный сохранённый intent мог пройти только структурный JSON-разбор | Проверяются адрес предсказанного деплоя, параметры действий, minters, стоимость, идентичность; каталог состояния требует 0700 | Rust-тесты повреждения состояния, неверной стоимости/адреса, блокировки и symlink |
| Компактные 64-байтные подписи не соответствуют исследованному entrypoint SeaDrop | Разрешён только канонический 65-байтный формат, проверяются low-s и восстановленный подписант | Payload unit tests и тесты контрактов |

## Оставшиеся ограничения

- OpenSea может не выдавать контрактным адресам Genesis-разрешения. API-ошибка не устраняется сменой языка, RPC или самостоятельной подписью кошелька. В частности, backend может проверять баланс самого minter; дети автоматически не финансируются.
- Смена маршрута на заранее неизвестный контракт останавливает CLI. Список доверенных адресов не обновляется автоматически по неподтверждённому ответу API.
- При смене состояния после симуляции ошибки могут расходовать газ. Изоляция сохраняет предыдущие успехи, но не делает failed-вызовы бесплатными. Прямой маршрут `quantity: 1` имеет обычную семантику revert SeaDrop.
- NFT adapter опирается на последовательные ID Genesis `totalMinted + 1`. Он не является универсальным ERC721 batch-minter.
- Максимум одного батча — 100, одной фабрики — 1024 ребёнка; фактический размер дополнительно ограничен газом сети и бюджетом.
- Dry-run без развёрнутых детей показывает только подготовку. Полная симуляция несуществующей фабрики через state overrides / `eth_simulateV3` в этот CLI не включена; предыдущие инструменты симуляции сохранены отдельно.
- Реестр защищает один локальный каталог. Удаление состояния, разные `--state-dir`, параллельный запуск с тем же EOA на другом сервере или внешние транзакции этого EOA нарушают предположение об одном отправителе. Неопределённая pending-транзакция требует разбирательства, автоматической отмены нет.
- `receiptObservedMs` измеряет наблюдение через reader, не финальность. Постоянный HTTPS/WSS-клиент не гарантирует первое место в блоке. Официальный sequencer по умолчанию используется через HTTPS; WSS feed не служит каналом отправки.

Практические команды: [RUST_GENESIS_MINT.md](../docs/RUST_GENESIS_MINT.md).

## Дополнение: одна команда проверки детей

Область следующей доработки: `check-children`, автоматический временный API-ключ, серверный launcher и установка на сохранённый EC2. Применены Rust, security и infrastructure/CLI профили; Solidity и SQL не изменялись.

Два замечания независимого ревью исправлены:

| Важность | Место и причина | Исправление и тест |
| --- | --- | --- |
| Medium | `rust-genesis-minter/src/main.rs:172`, `run.rs:998`: восстановление предыдущего pending mint могло завершить новую проверку кодом 0, хотя она не запускалась | Возвращается отдельная ошибка `CHILD_CHECK_NOT_PERFORMED`; EVM-тест подтверждает отсутствие новых API-запросов, транзакций и ложного `passed` |
| Medium | `rust-genesis-minter/src/main.rs:205`: проверялась только объявленная fulfillment-квота, а слишком низкая write-квота могла обнаружиться после платной подготовки | Все объявленные группы должны допускать два запроса; тест `write: 1/h` останавливается до приватника и деплоя |

Семантика `check-children`: ровно два ребёнка, minimum два, только signed-режим; `--send` разрешает исключительно подготовку. Получение временного API-ключа предшествует скрытому вводу приватника. Затем используются один клиент и одна партия из двух запросов; автоматического создания дополнительных ключей или повторного опроса нет. Финальная симуляция вызывается с `send=false` и без signer. `passed:true` выдаётся только после проверки обоих минтов и переводов.

Временный ключ возвращается сервисом в память клиента, наружу идут только числовые лимиты и срок. Обработаны невалидные/просроченные ответы, redirects, ограничения размера и времени, ошибки 401/403/429/503. Проверка реального официального endpoint создания ключа дала HTTP 201; ключ не сохранялся и не выводился. Это не проверка выдачи mint-разрешений детям.

После изменений: **31/31 Rust unit test**, **18/18 EVM CLI test**, `cargo fmt` и `cargo clippy --all-targets --all-features -- -D warnings` прошли. Новые EVM-сценарии дополнительно подтверждают две подготовительные транзакции и ноль mint-транзакций, переиспользование фабрики, отказ API до ввода приватника, 422 после подготовки с двумя неиспользованными детьми и запрет `quantity: 1` в этом режиме.

## Ошибка первого пользовательского запуска

Пользователь ввёл ключ самостоятельно. Фабрика `0xe90e51c3b5217012afc70573b57de363857b6f6d` успешно создана и сохранена; израсходовано `0.0000695821141 ETH`. Следующее чтение остановилось с `FACTORY_RUNTIME_IDENTITY_MISMATCH`. Полное сравнение реального runtime с артефактом подтвердило совпадение. Старый CLI воспроизвёл ту же ошибку, когда тестовый RPC после успешного receipt вернул `latest` из блока перед деплоем.

Исправление, проверки, порядок сохранения состояния и ограничения обновления описаны в [GENESIS_RPC_CONSISTENCY_REVIEW.md](GENESIS_RPC_CONSISTENCY_REVIEW.md). Создание детей и проверка их OpenSea-разрешений в этом пользовательском запуске не выполнялись.

Следующий запуск успешно создал двух детей на прежней фабрике, но не получил mint payload от OpenSea. Повторная диагностика API выявила недостаточный баланс у обоих minter-детей; основной кошелёк с ETH также не прошёл допуск к активному этапу. Полный результат, расходы и ограничения вывода: [GENESIS_CHILD_ELIGIBILITY_RESULT.md](GENESIS_CHILD_ELIGIBILITY_RESULT.md).
