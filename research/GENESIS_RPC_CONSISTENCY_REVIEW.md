# Code Review Report: состояние RPC после деплоя

## Findings

### [Medium, исправлено] Чтение `latest` могло возвращаться за блок подтверждённой транзакции

- File / line: `rust-genesis-minter/src/run.rs:436`, `chain.rs:62` (переход после деплоя и чтение head).
- Rule area: Rust, согласованность RPC, жизненный цикл подготовки.
- Related rule: проверять частичные результаты и порядок чтений после внешнего действия; ограничивать повторы.
- Impact: уже оплаченная подготовка останавливалась с ошибкой runtime; устаревшее число детей также могло приводить к неверному плану дальнейшей подготовки.
- Reachability: `recover` проверял runtime на точном блоке receipt, сохранял фабрику и очищал pending, затем `prepare` заново запрашивал `latest` без нижней границы номера блока.
- Evidence: реальная транзакция `0xb1880bd7b31d95822ac4c9bf0c2d3c0a9bf27423282b948191cfa191eff3bfaf` завершилась успешно; в журнале были `receipt` и `submission_complete`, затем остановка. На локальном EVM возврат `latest = receiptBlock - 1` воспроизвёл тот же порядок и `FACTORY_RUNTIME_IDENTITY_MISMATCH` на прежнем бинарнике.
- Recommended fix / implementation: сохраняется `last_receipt_block`; все следующие head/snapshot/quote используют минимум из подтверждённого и уже прочитанного номера блока. После трёх отстающих ответов программа останавливается; между ними 200 мс. Актуальный ответ не добавляет ожидания или RPC-запросов.
- Required tests: временное и постоянное отставание после factory deploy и prepareChildren, сохранение фабрики/расхода, отсутствие лишних отправок, восстановление границы после перезапуска.
- False-positive considerations: исходный запуск не записывал номер неудачного повторного чтения `latest`, поэтому историческое сетевое отставание установлено по порядку событий и точному воспроизведению, а не по сохранённому RPC-трейсу. Байткод реальной фабрики отдельно сравнен целиком с артефактом с подставленными immutable-адресами: совпадение всех 6299 байт.

### [Medium, исправлено до установки] Отступ в Python-функции проверки каталогов нарушал upgrade

- File / line: `scripts/install-genesis-check.sh:120`, generated `directory`.
- Rule area: файловые операции и проверка инфраструктуры.
- Impact: промежуточный вариант пытался создать существующий каталог состояния вместо проверки его прав.
- Evidence: обнаружено отдельным ревью и полным запуском сгенерированной программы в изолированном файловом дереве; до EC2 этот вариант не дошёл.
- Fix / tests: восстановлена вложенность условия, проверяются существующая установка, новая распаковка, права 0700/0755 и сохранность state/config.

## Domain Logic Assessment

- Invariants: сохранённая фабрика не пересоздаётся; газ подтверждённой транзакции учитывается один раз; pending очищается после проверки receipt; NFT-минт в `check-children` остаётся симуляцией.
- State transitions: проверенный receipt атомарно сохраняет номер блока вместе с расходом и адресом фабрики. Отмена неотправленного intent не сбрасывает эту границу.
- Authorization: владелец/получатель, скрытый ввод ключа и денежные пределы сохранены.
- Consistency: оценка газа, подтверждённый nonce и баланс читаются на одном свежем номере блока. Pending nonce ниже подтверждённого вызывает отдельную ошибку до отправки; более высокий означает занятую очередь кошелька.
- Open questions: получение настоящих OpenSea-разрешений детям ещё не проверено.

## Rust Quality Assessment

- Error handling: число попыток ограничено тремя; сообщение содержит требуемый и полученный блок. Runtime mismatch теперь содержит адрес, номер блока, ожидаемый/фактический хеш и длину кода.
- Type safety: номера блоков — `u64`, поле сохранённого receipt опционально для чтения старой схемы.
- Async/concurrency: только асинхронная задержка на отставании; дисковая запись остаётся в существующем blocking worker.
- Unsafe: не добавлен.
- Performance: число запросов нормального пути сохранено; новый цикл действует только при отставании. Новые сетевые задержки транзакций не измерялись.

- Исправленный Rust: 32 unit tests, formatter и clippy со всеми предупреждениями как ошибками прошли.
- Исправленный CLI: полный набор 25 EVM-сценариев прошёл (48.98 с), включая семь новых проверок head lag, перезапуска, pending nonce и неверного runtime. Бинарник между этими прогонами не менялся.

## Recommendations

- Must fix before update: известных блокирующих замечаний после локальных проверок и независимого ревью нет.
- Для сервера: обновить только бинарник/launcher, выполнить read-only preflight на существующей фабрике, сохранить новый checkpoint журнала до ввода ключа пользователем.

## Residual Risk

- RPC остаётся источником состояния. Нижняя граница номера блока не является проверкой финальности или защитой от недостоверного RPC на том же номере блока.
- После трёх отстающих ответов программа намеренно останавливается; дополнительные отправки не выполняются.
- Старый state без `last_receipt_block` читается новой версией; граница начинает сохраняться со следующего проверенного receipt. Старый бинарник не понимает новое поле, поэтому откат бинарника после новых транзакций потребует отдельной проверки совместимости; state удалять нельзя.
- Проверка OpenSea и симуляция настоящих двух минтов требуют следующего запуска с ключом, введённым пользователем. Обновление само не создаёт детей и не выполняет минт.
