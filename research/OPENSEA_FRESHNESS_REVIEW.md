## Как устроены текущие маршруты

```text
batch/setup/start → фиксированная фабрика → новые helpers → SeaDrop.mintPublic → Genesis → перевод NFT получателю
mint.mjs --payload → файл → проверки подписи → SeaDrop.mintSigned → Genesis
Rust benchmark → отдельные тестовые NFT и фабрика
```

| Изменение | Что происходит сейчас |
| --- | --- |
| OpenSea выдаёт другую серверную подпись | Публичной фабрике подпись не нужна. Signed CLI сам новую не получает |
| Меняются сроки публичного этапа | `readPublicStage` перечитывает их; перенос позже продолжает ожидание |
| Старт переносится раньше | Обнаружение может запоздать примерно на интервал обновления условий |
| Публичный этап становится платным/отключается | Warm mode останавливается, сам к другому типу минта не переходит |
| Меняется разрешённый SeaDrop / fee recipient | Фиксированный маршрут может стать недействительным; финальная симуляция обычно обнаружит это до отправки |
| OpenSea переводит коллекцию/минт на другие адреса | Автоматического обнаружения и перехода нет; старые адреса могут оставаться исполнимыми |
| Изменяется состояние после финальной симуляции | Отправленная транзакция может откатиться с расходом газа |

### Адреса и фабрика

`mint.mjs:12` фиксирует NFT, SeaDrop и fee recipient. Solidity содержит те же константы (`contracts/RareFriendsBatchMinter.sol:4`); развёрнутая фабрика не умеет менять их. JSON-конфигурация их не переопределяет. Новые адреса требуют пересмотра реализации/артефакта и нового деплоя; редактирование JSON не изменяет существующий байткод.

Начальная подготовка проверяет точный hash NFT, наличие кода SeaDrop и артефакт/владельца/получателя фабрики (`batch.mjs:169`). В warm preflight используется подготовленная транзакция; полная начальная проверка runtime заново не проводится (`batch.mjs:217`). Полноценного мониторинга разрешённых SeaDrop, подписантов, fee recipient и соответствия странице OpenSea нет.

### Ожидание и симуляция

`lib/warm.mjs` обновляет условия примерно раз в `keepAliveIntervalMs` (**10 секунд по умолчанию**, плюс RPC). В последние 15 секунд `pollIntervalMs` (**250 мс**) означает более частое чтение времени блока, а не свежую подпись или все условия каждые 250 мс. Перед выходом из ожидания конфигурация читается повторно.

После ожидания выполняются финальные `eth_call` и `eth_estimateGas`, затем комиссия/nonce/баланс, подпись и отправка (`batch.mjs:471`). Верхнего предела возраста симуляции и повторного формирования транзакции при изменении условий на этом промежутке нет. Чтения `latest` не являются одним атомарным снимком. Симуляция не резервирует состояние блокчейна.

Фабрика непосредственно при исполнении читает текущий public drop и остаток до создания helpers (`RareFriendsBatchMinter.sol:97`). Это учитывает уменьшение supply от предшествующих транзакций, но любая ошибка helper/перевода откатывает весь batch. Другие транзакции не вклиниваются между действиями одной EVM-транзакции; возможные внешние callback-вызовы не равнозначны такой конкуренции.

### Подписи

`mint.mjs:345` загружает payload один раз. Проверяются сеть, фиксированные адреса, minter, EIP-712-подписант и его текущие ограничения, время, лимиты, fee recipient; `eth_call` дополнительно проверяет одноразовость и контрактные ограничения. При недействительной подписи CLI завершится, а не запросит другую.

Новый ответ OpenSea с другой подписью **сам по себе не отменяет предыдущую**: SeaDrop проверяет конкретный digest, сроки и актуальные разрешения. Проблемы возникают при истечении срока, использовании digest, отзыве/ограничении подписанта или других изменениях состояния. Подпись разрешения OpenSea и подпись транзакции нашего кошелька — разные подписи.

По [исходнику SeaDrop](https://github.com/ProjectOpenSea/seadrop/blob/main/src/SeaDrop.sol), разрешение привязано к minter, NFT, fee recipient, параметрам и salt; EIP-712 domain также включает сеть и SeaDrop. Одно разрешение для EOA нельзя перенести на десять helpers. Для signed batch нужна отдельная поддерживаемая схема и действительные разрешения для соответствующих minter; фабрика не создаёт eligibility.

## Что улучшать

1. Добавить проверку текущего типа этапа и доверенных адресов при подготовке, мониторинг событий конфигурации с повторным чтением состояния, сверку после разрыва соединения. Последние 1–2 минуты чаще обновлять состояние в рамках RPC-лимитов. Уже сейчас допустим `keepAliveIntervalMs: 1000`; это уменьшает задержку обновления расписания, но не добавляет миграцию или получение подписей.
2. Любое значимое изменение должно отменять подготовленный payload и требовать новой проверки перед подписью. Не менять calldata после подписания и не создавать замену вслепую, если предыдущая транзакция уже могла уйти.
3. Для signed mint интегрировать официальный [Build mint transaction data](https://docs.opensea.io/reference/build_drop_mint_transaction): API key, slug, minter и quantity; ответ содержит target, calldata и value. Обновлять разрешение с учётом его срока и допустимости. Фактическая выдача для Genesis/нашего адреса не проверена, API key не запрашивался.
4. Декодировать и проверять любой новый API-ответ: сеть, NFT, допустимый executor, minter/получатель, цена, лимиты, подпись. Документированный API автоматически выбирает первый подходящий активный этап, поэтому запрос не гарантирует именно публичный маршрут.
5. Если нужна переносимая фабрика, разработать отдельную проверенную реализацию с явно ограниченными целями/режимами. Существующий контракт не станет поддерживать signed mint от замены RPC или языка клиента.
6. Добавить ограничение возраста финальной проверки и тесты смены адресов, отзыва подписанта непосредственно перед отправкой, переноса старта раньше, недоступности API, смены public→signed и устаревшего payload.

## Проверка и ограничения

Независимый локальный запуск `node --test test/mint.test.mjs test/warm.test.mjs`: **47/47 пройдено**. Уже покрыты переносы расписания, платный/отключённый этап, отзыв подписанта/fee recipient и использованная подпись. Это mocked unit tests, не успешный Genesis mint.

Предыдущие реальные Rust-замеры проверяли транспорт и свои тестовые контракты, без OpenSea API. Они не доказывают готовность к динамическим разрешениям Genesis. Полного исходника Genesis и персонального свежего mint payload в этой проверке нет; прежнее исследование байткода остаётся отдельным ограниченным анализом.
