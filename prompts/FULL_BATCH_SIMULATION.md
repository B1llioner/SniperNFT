Готовая инструкция для агента, который будет реализовывать и запускать тест. Команды `simulate:full` ниже — требование к будущей реализации; сейчас такой команды в проекте нет.

## Задача

Работай в `/Users/dmitriy/Projects/VinosNFT`. Исходное состояние сохранено в локальном Git: ветка `main`, коммит `82617a7`. Обновление делай в `test/full-batch-simulation`; сохраняй исходную версию в `main`.

Реализуй и выполни воспроизводимый полный тест Rare Friends Genesis на состоянии Robinhood Chain Mainnet, chain ID **4663**:

**Пустой тестовый кошелёк → получение 0.1 виртуального ETH → настоящий CREATE фабрики → настройка тестового окна минта → ожидание открытия → одна транзакция `mintBatch(10, 10)` → все 10 NFT у этого кошелька.**

## 2. Выбор RPC и метода

Первоначально пользователь назвал `eth_simulateV3`. На момент проверки получены следующие результаты:

| Endpoint | `eth_simulateV1` | `eth_simulateV3` |
| --- | --- | --- |
| `https://rpc.mainnet.chain.robinhood.com` | Работает | `-32601` |
| `https://robinhood-rpc.publicnode.com` | Работает | `-32601` |
| `https://sequencer.mainnet.chain.robinhood.com` | `-32601` | `-32601` |

На двух обычных RPC с `validation: true` прошли два зависимых перевода: пополнение на 0.1 ETH и последующая трата получателем 1 wei. Без пополнения и без резерва на газ получен `insufficient funds`. Это пока проверка переноса состояния и платёжеспособности, а не доказательство полного CREATE → mint.

Повтори ограниченную проверку возможностей. Используй **`eth_simulateV1`** при подтверждённой поддержке. V3 допустим только при наличии документации конкретного провайдера и успешного запроса по этой документации; не придумывай его формат. Неправильные параметры и HTTP 400 сами по себе не доказывают поддержку метода.

Для V1 используй один последовательный запрос с `blockStateCalls`, `validation: true`, `traceTransfers: true`, `returnFullTransactions: true` и закреплённым родительским блоком вторым параметром. Все зависимые вызовы должны видеть изменения предыдущих. Формат сверяй со [спецификацией Execution APIs](https://ethereum.github.io/execution-apis/api/methods/eth_simulateV1/) и [описанием Geth](https://geth.ethereum.org/docs/interacting-with-geth/rpc/ns-eth).

Публичный sequencer сейчас не поддерживает эти методы симуляции. Его возможное применение для последующей реальной отправки оценивается отдельно. Адреса RPC, sequencer и feed перечислены в [документации Robinhood](https://docs.robinhood.com/chain/connecting/); WebSocket feed не является методом симуляции или отправки транзакций.

### Один запрос с несколькими транзакциями

Используй принцип из предоставленного пользователем примера: несколько объектов транзакций в `calls` одного `eth_simulateV1` последовательно меняют общее виртуальное состояние. Если моделируется десять транзакций, это десять объектов вызова, а не десять независимых запросов. Дополнительные вызовы подготовки и assertions учитывай отдельно. Наш `mintBatch`, создающий десять helper, сам остаётся одним объектом вызова.

Схема ниже иллюстрирует структуру, переменные должны быть построены реализацией:

```js
await provider.send('eth_simulateV1', [{
  validation: true,
  traceTransfers: true,
  returnFullTransactions: true,
  blockStateCalls: [
    {
      stateOverrides: initialVirtualFunding,
      blockOverrides: { time: beforeStartHex },
      calls: preparationCalls, // Пополнение, CREATE, локальная настройка окна.
    },
    {
      blockOverrides: { time: afterStartHex },
      calls: [
        ...competitorMintCalls, // Чужие минты перед нашей транзакцией.
        ourPreviouslyPreparedMint, // Та же calldata; остаток читает фабрика.
        ...assertionCalls,
      ],
    },
  ],
}, pinnedParentBlockHex]);
```

Ограничивай суммарный газ каждого виртуального блока и запроса. При превышении раскладывай подготовку и конкурентов по нескольким последовательным виртуальным блокам внутри того же запроса; не повышай лимит газа, чтобы скрыть невозможный сценарий.

### Быстрый режим с виртуальным контрактом

Добавь явно обозначенный режим `virtual-factory` по примеру пользователя. Сначала прочитай `eth_getCode(factory, pinnedBlock)`. Если код есть, проверь его совместимость и настоящие owner/recipient. Если кода нет, можно только на время симуляции подставить runtime фабрики через `stateOverrides[factory].code` и нужное тестовое состояние. Реальное развёртывание при этом не происходит.

У этой фабрики `owner` и `recipient` — **immutable**, адреса встроены в runtime. Используй `immutableReferences` артефакта и существующую логику `scripts/simulate-rpc-batch.mjs`, затем проверь getters в виртуальном состоянии. Пример `stateDiff[slot0] = owner` из скриншота предназначен для другого контракта: у нас slot 0 хранит защиту от повторного входа `entered`, а не owner. Не копируй такую запись.

Этот быстрый режим нужен для проверки минта до фактического деплоя. В отчёте отделяй его от `full-create`: подставленный runtime не доказывает работу конструктора или расход газа на CREATE. Для основного полного теста продолжай использовать настоящий CREATE внутри симуляции.

## 4. Деплой и локальное время

От mint wallet выполни создание фабрики из актуального **creation bytecode с аргументом конструктора `recipient = mint wallet`**. У транзакции создания нет адреса `to`. Рассчитай CREATE-адрес из отправителя и nonce; проверь реально созданный код, `owner()` и `recipient()`, учитывая immutable-поля. Подстановка готового runtime вместо CREATE не выполняет эту часть задачи.

**В текущих factory/helper нет собственного расписания.** Фабрика читает окно из `SeaDrop.getPublicDrop(nft)` и сравнивает его с `block.timestamp`. Helper минтит и переводит NFT в своём конструкторе; предварительно создать десять helper, а потом вызвать у них минт нельзя.

Сделай два явных режима времени:

- **`local-window` — основной тест с локальным расписанием.** Выбери `T = timestamp родительского блока + 60 секунд`, окно `[T, T + 3600]`. В подготовительной части симуляции вызови на Genesis `updatePublicDrop(address,(uint80,uint48,uint48,uint16,uint16,bool))` от адреса, прочитанного через `owner()`. Сохрани цену, лимит, feeBps и ограничение fee recipient; измени только начало и конец. Этот метод NFT должен сам передать настройки SeaDrop. Проверь успешность вызова и прочитай новое окно обратно. Селектор восстановлен из байткода (`0x1b73593c`); не объявляй admin-путь рабочим без фактического исполнения. Имперсонация owner нужна только для тестовой подготовки; прав владельца у mint wallet нет. Если owner — контракт, явно отметь, что его реальный механизм авторизации здесь не воспроизводится.
- **`onchain-window` — контроль с настоящим расписанием.** Не меняй настройки этапа. Используй время блоков до реального открытия и внутри реального окна. Родительский блок должен позволять двигать время только вперёд. При необходимости закрепи подходящий исторический блок и обозначь тест как исторический.

Если локальная настройка через реальный setter невозможна, покажи причину и выполни доступный контроль с настоящим расписанием. Не подменяй незаметно один режим другим.

Для V1 задавай возрастающие номера блоков и `blockOverrides.time` явно: подготовка до T, минт в T + 1. Для локального fork управляй timestamp и майнингом. Системные часы машины и `Date.now()` не открывают этап в EVM. Семантика времени и состояния описана в [примечаниях к eth_simulateV1](https://ethereum.github.io/execution-apis/docs/ethsimulatev1-notes/).

Код Genesis, SeaDrop, ERC6551 Registry, реализации аккаунтов и transfer hook должен оставаться настоящим. Не заменяй эти зависимости заглушками в положительном сценарии.

## 5. Минт и точность симуляции

После пополнения, деплоя и настройки окна выполни **одну транзакцию** от mint wallet к созданной фабрике: `mintBatch(10, 10)`, `value = 0`. Она должна создать десять helper и передать десять NFT этому же кошельку.

- Укажи корректные nonce всех отправителей. При исходном nonce 0 у mint wallet: CREATE — nonce 0, mint — nonce 1. Служебные вызовы в V1 выполняй от observer, чтобы они не меняли эту последовательность. Учитывай их собственные nonce и газ.
- Используй ненулевые комиссии, явные gas limit и текущую базу для выбора max fee. Записывай base fee каждого виртуального блока. Не отключай `validation` и не обнуляй base fee ради успешного результата.
- Проверяй доступность `value + gasLimit × maxFeePerGas` перед каждой транзакцией. Списанную комиссию и оставшийся баланс измеряй отдельно от этого верхнего резерва. Уточняй, что именно backend учитывает из Nitro/L1 fees; расхождения фиксируй.
- Получай результаты и проверки **внутри той же последовательности V1**: последующие вызовы getters и при необходимости отдельный тестовый observer-контракт для чтения BALANCE/кода. Его создание и расходы укажи отдельно. Обычный удалённый `eth_call` после завершения V1 не видит виртуальную фабрику и NFT.
- JSON-RPC batch из независимых `eth_call` не заменяет такую последовательность. Зависимые операции выполняются по порядку; в параллель можно вынести независимые чтения и сравнение RPC.
- Различай ошибку всего RPC-запроса/валидации и `status: 0x0` отдельного EVM-вызова. Проверяй все нужные статусы, включая служебные assertions. Соблюдай ограничения RPC на общий газ, число блоков, размер ответа и тайм-аут.

### Гонка: проверка остатка до первого helper

Сохрани проверку в самом `mintBatch` **до цикла и любого CREATE helper**:

```solidity
(, uint256 minted, uint256 maximum) = nft.getMintStats(address(0));
uint256 remaining = maximum > minted ? maximum - minted : 0;
uint256 count = remaining < maxCount ? remaining : maxCount;
if (count < minCount) revert InsufficientSupply(remaining, minCount);
// Только теперь создавать count helper и минтить.
```

Этот алгоритм уже есть в `contracts/RareFriendsBatchMinter.sol`. Сначала докажи его поведение тестами; изменение production-байткода для дублирующей проверки не требуется. Прогноз RPC не должен заменять чтение состояния внутри транзакции. Текущий CLI передаёт максимум и минимум, а receipt проверяет фактический результат в этих пределах.

Остальные транзакции не вклиниваются между действиями одного EVM-вызова. В гонке меняется состояние **перед** нашей транзакцией; дополнительных перечитываний supply между helper ради чужих транзакций не требуется. Исключения вроде сбоя внешней зависимости или нехватки газа исследуются отдельно.

Создай состояние 910/1024 настоящими тестовыми минтами на подходящем fork; например, из снимка с 906 сначала сминти 4. Не подставляй только значение supply, оставляя несогласованные владельцев и счётчики. Каждый сценарий начинай с одинакового снимка:

| Порядок исполнения после подготовки при 910/1024 | Наша неизменная calldata | Ожидание |
| --- | --- | --- |
| Наша транзакция первая | `mintBatch(1024, 1)` | 114 NFT, если хватает газа и бюджета |
| 10 чужих кошельков сминтили по 1 → наша | `mintBatch(1024, 1)` | 104 NFT; чужие вызовы и наш идут одним запросом V1 |
| Конкуренты забрали 20 → наша | `mintBatch(1024, 1)` | 94 NFT |
| Конкуренты забрали 108 → наша | `mintBatch(1024, 1)` | 6 NFT, успешная транзакция |
| Конкуренты забрали 113 → наша | `mintBatch(1024, 1)` | 1 NFT через фабрику |
| Конкуренты забрали все 114 → наша | `mintBatch(1024, 1)` | Ранний `InsufficientSupply(0, 1)` |
| Конкуренты забрали 108 → строгий контроль | `mintBatch(114, 114)` | Ранний `InsufficientSupply(6, 114)` |

Особенно проверь устаревшую успешную симуляцию: сначала получи прогноз 114, подготовь calldata и gas limit, затем исполни конкурентов и отправь ранее подготовленную транзакцию без подгонки её количества к новому остатку. Для V1 это отдельный контрольный запрос с прогнозом и затем полный последовательный запрос с конкурентами; локальный fork позволяет также проверить заранее подписанные bytes.

Для десяти отдельных конкурентов используй десять новых тестовых EOA, предварительно виртуально обеспеченных газом, и настоящие `SeaDrop.mintPublic(..., 1)` с корректным fee recipient. Эти десять чужих вызовов плюс наш составляют 11 mint-вызовов; число объектов в запросе и число NFT не следует смешивать. Чужие nonce и пожизненные лимиты минта тоже проверяются.

При sold out отправь локальную тестовую транзакцию с большим корректным gas limit, дождись receipt с ошибкой и измерь **фактически использованный газ**. По trace проверь отсутствие `CREATE`/`CREATE2` и вызовов `SeaDrop.mintPublic`; supply, NFT-балансы и nonce самой фабрики не должны измениться. Nonce отправителя при включённой неуспешной транзакции увеличивается и газ за проверки списывается — это ожидаемо.

Ранний `revert` не расходует автоматически весь gas limit: неиспользованный газ не оплачивается. При `out-of-gas` может израсходоваться весь лимит, а сбой позднего helper может откатить выполненные минты и потратить газ за уже сделанную работу. Проверка supply защищает от нехватки остатка, но не отменяет эти отдельные причины ошибок. Не обещай нулевой комиссии при проигранной гонке.

Для режима «весь остаток» отдельно проверь, помещается ли партия в ограничения Nitro и бюджет. Заголовочный `block.gasLimit` может быть служебным большим значением; проверь реальный предел через ArbGasInfo, включая `getMaxTxGasLimit()`. При проверке 15 сентября 2026 года RPC возвращал 32 000 000. Не используй это число как вечную константу production-кода. Семантику и компоненты комиссии сверяй с [ArbGasInfo](https://docs.arbitrum.io/arbitrum-essentials/precompiles/reference#arbgasinfo). Если полный остаток не помещается, сообщи об ограничении до отправки; автоматическое дробление на несколько реальных транзакций требует отдельной реализации с новой проверкой перед каждой.

Уже измеренное ограничение: локальный контроль 114 NFT прошёл с gas limit 32 000 000 и фактическим расходом 24 773 734. Но оценка Anvil 27 702 758 с полным запасом 20% даёт 33 243 310. Тест явно использовал меньший запас; production `gasQuote` такую оценку отклоняет. Не представляй этот отдельный контроль как успешный запуск production CLI с неизменёнными настройками.

## 6. Проверки результата

Успех фиксируй только при выполнении всех основных условий:

1. Пополнение и CREATE успешны; owner и recipient фабрики равны mint wallet. После начального пополнения баланс кошелька не меняли overrides.
2. Минт успешен; V1 returnData декодируется как 10; есть `BatchMinted(..., 10)` и десять `TokenMinted` с разными helper и token ID.
3. Счётчик выпуска Genesis вырос на 10, NFT-баланс mint wallet вырос на 10, `ownerOf` каждого нового токена равен mint wallet.
4. Каждый helper сминтил один NFT по `getMintStats(helper)` и в конце владеет нулём NFT. Логи Genesis подтверждают пары переводов `0x0 → helper → mint wallet` для каждого токена.
5. Связанные ERC6551-аккаунты проверены через реальные события/registry и доступный виртуальный код; transfer hook действительно участвовал. Не требуй заранее угаданного числа дополнительных аккаунтов — установи поведение по коду и исполнению.
6. Отдельно показаны газ и комиссия funding, factory CREATE, mint, тестовой настройки/проверок; остаток из 0.1 ETH измерен. `traceTransfers` не содержит списаний за газ, поэтому одних его логов для проверки комиссии недостаточно.
7. После удалённой симуляции виртуальные изменения отсутствуют в настоящей сети. Сравни баланс/nonce тестовых адресов и код CREATE-адреса на закреплённом состоянии и после запроса.

Негативные сценарии запускай из одного исходного снимка отдельными прогонами: без пополнения; минт до открытия (`InactiveStage`); вызов чужим отправителем (`NotOwner`); недостаточный бюджет комиссии. Проверь ошибку и отсутствие новых NFT. При контролируемом сбое helper/перевода проверь атомарный откат всего минта. Для искусственных неисправностей допускается отдельный локальный fixture с явно указанными изменениями, не смешанный с положительным тестом.

## 7. Проверка настоящего запуска на локальном fork

V1 проверяет исполнение EVM, но пропускает проверку подписей и не запускает наш процесс ожидания или сетевую рассылку. Поэтому дополнительно проверь полный путь существующего launcher на **локальном Anvil fork**: пополнение пустого тестового кошелька → `setup`/деплой → запись отдельного временного state-файла → тёплое ожидание → открытие локального блока → финальная симуляция → подпись → отправка → receipt → владельцы NFT.

Используй ту же фабрику, calldata и конфигурацию количества. Повторный запуск с сохранённой фабрикой должен использовать прежний адрес. Для проверки повторного запуска сохрани снимок fork и копию временного state-файла после успешного деплоя и записи статуса `deployed`, но до минта; восстанавливай их согласованно. `evm_revert` не откатывает файлы на диске. Если проверяешь fan-out, направляй несколько локальных RPC-прокси в один fork и подтверждай один hash и одну выполненную транзакцию.

Anvil слушает `127.0.0.1`. Разрешай отправку только в поднятую тестом локальную ноду после проверки её клиента и chain ID. Fork сохраняет chain ID 4663, поэтому одной проверки chain ID недостаточно. Используй новые тестовые ключи и временные конфиги/state; рабочие `.env`, `batch.config.json` и `.state/` пользователя не затрагивай. Внешние RPC используются для чтения и симуляции.

`gasQuote` требует работающий `ArbGasInfo.getMaxTxGasLimit()`, который обычный Anvil может не реализовывать. Для локального теста launcher допустим явно описанный RPC-адаптер: только на этот информационный getter он возвращает проверенное значение из исходной сети, остальные вызовы направляет в Anvil. Запиши источник/блок значения и эту особенность теста. Не отключай production-проверку лимита и не подменяй исполнение NFT/SeaDrop успешными ответами.

Если RPC не поддержит полный CREATE/нужные overrides, выполни доступный сценарий на fork и явно сообщи, какая часть V1 осталась неподтверждённой. Локальный Anvil не воспроизводит в точности sequencer, конкуренцию за место и все особенности комиссий Nitro. Не выдавай время симуляции за скорость включения в mainnet-блок.

## 8. Что предоставить после реализации

- Скрипт полного теста, например `scripts/simulate-full-batch.mjs`, и готовую команду `npm run simulate:full` с выбором `--backend rpc|anvil`, режима времени и родительского блока. Документируй фактически реализованные аргументы.
- Пример тестового конфига: количество 10, минимум 10, пополнение 0.1 ETH, задержка открытия 60 секунд, длительность 3600 секунд, RPC и конечные тайм-ауты. Финансовые величины передавай строками, без потери точности Number.
- Машиночитаемый отчёт `research/full-batch-simulation.json`: backend/метод, версия клиента, блок/hash/время, все overrides, параметры транзакций, статусы, ошибки, адрес фабрики/helper, NFT ID и владельцы, газ/комиссии/балансы, результаты assertions. Секреты и ключи в отчёт не включай.
- Замеры по этапам: чтения, подготовка, выполнение V1; отдельно локальные ожидание, симуляция, подпись, RPC-ответ и receipt. Укажи число прогонов и среду измерений.
- Запусти подходящие тесты и оба доступных полных сценария. В итоговом отчёте раздели фактически пройденные проверки, ограничения и то, что выполнить не удалось. Сохрани изменения в тестовой ветке.

Критерий завершения: воспроизводимая команда доказывает минт десяти NFT в контрольном полном сценарии, адаптацию к уменьшившемуся остатку в гонке и ранний отказ при sold out с измеренным расходом газа. Один успешный RPC-ответ или подставленный runtime фабрики этого не доказывают.
