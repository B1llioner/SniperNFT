# Несколько Rare Friends Genesis с одного кошелька

[`batch.mjs`](batch.mjs) использует **один кошелёк с ETH в Robinhood Chain, chain ID 4663**. Этот кошелёк развёртывает фабрику, вызывает минт и по умолчанию получает все NFT. Отдельно пополнять вспомогательные адреса или создавать для них приватные ключи не требуется.

Маршрут выбирается автоматически по настройке `quantity`:

- **`1`** — кошелёк напрямую вызывает `SeaDrop.mintPublic`. Фабрика и помощники не нужны; поле `factory` игнорируется. NFT получает сам отправитель.
- **Больше `1`** — сначала один раз развёртывается [`RareFriendsBatchMinter`](contracts/RareFriendsBatchMinter.sol). Затем `mintBatch` создаёт вспомогательные контракты: каждый минтит один NFT через `SeaDrop.mintPublic` и сразу передаёт его основному кошельку. Все выбранные минты и переводы входят в одну транзакцию и выполняются последовательно. Ошибка любого из них откатывает всю партию.

В обоих режимах используется одинаковая схема параллельной отправки по RPC. Встроенное создание ERC-6551 аккаунта самим Genesis остаётся частью его минта.

Запуск заранее с `mint --wait`, настройка запаса комиссии и команды измерения скорости: **[RUNNING.md](RUNNING.md)**.

Для обычного использования: `npm run launch -- --config batch.config.json --send` разворачивает или находит сохранённую фабрику, проверяет её и запускает ожидание. `npm run start -- --config batch.config.json --send` работает с уже существующей фабрикой. Адрес и незавершённый деплой сохраняются автоматически; подробности восстановления и блокировки — в [RUNNING.md](RUNNING.md).

## 1. Подготовка и количество

Из каталога проекта, с Node.js 18.18 или новее:

```sh
npm ci
npm test
cp -n batch.config.example.json batch.config.json
```

Настройки берутся из явно переданного `--config`. Шаблон: [`batch.config.example.json`](batch.config.example.json).

```json
{
  "quantity": 10,
  "minQuantity": 1,
  "recipient": null,
  "factory": null,
  "rpcUrls": [
    "https://robinhood-rpc.publicnode.com",
    "https://rpc.mainnet.chain.robinhood.com"
  ],
  "concurrency": 2,
  "attempts": 2,
  "retryDelayMs": 250,
  "maxGasCostEth": "0.003",
  "maxFeeMultiplier": 4,
  "receiptTimeoutSeconds": 120,
  "waitTimeoutSeconds": 21600,
  "pollIntervalMs": 250,
  "keepAliveIntervalMs": 10000
}
```

| Настройка | Значение |
| --- | --- |
| `quantity` | Желаемый максимум, от 1 до 1024. По умолчанию допускается доступный остаток меньше этого числа. |
| `minQuantity: 1` | Режим по умолчанию: `min(quantity, остаток выпуска)`, минимум один NFT. Значение `null` или отсутствие поля также означает `1`. |
| `minQuantity: N` | Явный минимально приемлемый результат. Для строго заданного количества поставьте `minQuantity` равным `quantity`. |
| `recipient: null` | Получатель совпадает с отправляющим кошельком. |
| `factory` | Нужен при `quantity > 1`. После развёртывания впишите сюда адрес своей фабрики. |
| `rpcUrls` | От 1 до 8 RPC. Перед использованием проверяется chain ID каждого. |
| `concurrency` | Число одновременных отправок в RPC: 1–8. |
| `attempts` | Максимум попыток на RPC, включая первую: 1–5. |
| `retryDelayMs` | Пауза между раундами повторов: 0–5000 мс. |
| `maxGasCostEth` | Предел `gasLimit × maxFeePerGas` для каждой отправляемой транзакции; по умолчанию 0.003 ETH. |
| `maxFeeMultiplier` | Множитель текущей base fee, целое 1–20. В шаблоне `4`; при отсутствии поля сохраняется прежнее значение `2`. |
| `receiptTimeoutSeconds` | Время опроса receipt: 1–600 секунд, по умолчанию 120. Отдельный RPC-запрос ограничен 20 секундами. |
| `waitTimeoutSeconds` | При `--wait`: максимум подготовки и ожидания после первичной проверки сети, 1–86400 секунд; по умолчанию 21600 (6 часов). |
| `pollIntervalMs` | При `--wait`: пауза между чтениями времени блока в последние 15 секунд до этапа; 100–10000 мс, по умолчанию 250. Время ответа RPC прибавляется к паузе. |
| `keepAliveIntervalMs` | При `--wait`: интервал обновления этапа и фоновых проверок RPC, 1000–60000 мс, по умолчанию 10000. |

**1024 — технический предел количества, а не обещание вместить столько минтов в одну транзакцию.** Фактический максимум ограничен остатком выпуска, лимитом газа блока и выбранным пределом расходов. Скрипт сначала выполняет симуляцию и оценивает газ с запасом 20%. Если оценка не проходит, уменьшите `quantity` и повторите dry-run.

Например, при `quantity: 10` скрипт передаёт фабрике максимум 10 и минимум 1: осталось 20 — минтится 10; осталось 3 — минтится 3; осталось 1 — минтится 1. Остаток определяется внутри самой транзакции в момент исполнения. Другие транзакции не могут вклиниться между её минтами. Если до отправки симуляция обнаруживает нулевой остаток, отправки не будет. Если выпуск закончится уже после симуляции, транзакция может откатиться с расходом газа.

Количество, показанное симуляцией, может отличаться от результата: остаток выпуска меняется до включения транзакции. Фактическое количество должно оставаться внутри указанных границ; оно проверяется по событиям в receipt. Это не режим пропуска неудачных помощников: ошибка отдельного минта или перевода всё равно откатывает всю партию. Лимит газа, бюджет и активность этапа по-прежнему обязательны; автоматического подбора количества по бюджету нет.

### Скорость и газ при доступном остатке

Режим не добавляет сетевых запросов, подписей или транзакций: меняется минимально допустимое количество в уже существующем вызове фабрики. Проверка остатка уже была в её коде. При одинаковом фактическом количестве NFT существенного удорожания от разрешения меньшего остатка не ожидается; точная итоговая комиссия зависит от сети. Если минтится меньше NFT, создаётся меньше помощников и выполняется меньше переводов, поэтому газ обычно ниже. Увеличенный `gasLimit` задаёт потолок, а не фиксированную плату за все запрошенные NFT. Комиссия включает использованный газ L2 и публикацию данных в L1; обычная оценка RPC учитывает обе части ([документация сети](https://docs.robinhood.com/chain/gas-and-fees/)).

Сам контракт фабрики не изменён, повторное развёртывание для этого режима не требуется. В старом конфиге `minQuantity: null` теперь также включает доступный остаток; явное числовое значение сохраняет заданный минимум.

Флаги CLI имеют приоритет над конфигом. Например, `--quantity 5 --min-quantity 1`; также поддерживаются названия `--max-count` и `--min-count`. Выбор маршрута зависит от заданного `quantity`: партия с `quantity: 10, minQuantity: 1` использует фабрику даже при остатке в один NFT.

## 2. При количестве больше одного: развернуть фабрику один раз

При `quantity: 1` пропустите этот раздел. Команда `deploy` с таким конфигом сообщает, что фабрика не требуется, и ничего не отправляет.

Подставьте адрес своего кошелька. Без `--send` выполняются только проверки, симуляция создания контракта и оценка газа:

```sh
node batch.mjs deploy --config batch.config.json --from 0xYOUR_WALLET_ADDRESS
```

Для реальной отправки передайте приватный ключ локально через переменную окружения `PRIVATE_KEY`. Пример скрытого ввода для **zsh**:

```sh
read -rs 'PRIVATE_KEY?Приватный ключ: '
export PRIVATE_KEY
node batch.mjs deploy --config batch.config.json --send
unset PRIVATE_KEY
```

Формат ключа — `0x` и 64 шестнадцатеричных символа. Не записывайте ключ в JSON и не передавайте его в чате. С `--send` адрес отправителя определяется по ключу; если также передать `--from`, адреса должны совпасть.

После подтверждения скрипт выводит `status: deployed`, адрес `factory`, `owner` и `recipient`, а также автоматически сохраняет фабрику в `.state/factory-4663-АДРЕС_КОШЕЛЬКА.json` в каталоге проекта. Повторный `deploy` проверяет и использует сохранённую фабрику. Команды `launch` и `start` читают этот файл автоматически. Для старого прямого `batch.mjs mint` запишите адрес в поле `factory` конфига или передайте `--factory`. Владелец и получатель фабрики фиксируются при создании; для схемы с одним кошельком оставьте `recipient: null`.

Развёртывание фабрики само по себе NFT не минтит. Его можно выполнить до начала публичного этапа.

## 3. Симуляция и отправка партии

Когда публичный этап активен:

```sh
node batch.mjs mint --config batch.config.json --from 0xYOUR_WALLET_ADDRESS
```

При `quantity > 1`, если адрес фабрики ещё не записан в конфиг, передайте его явно:

```sh
node batch.mjs mint --config batch.config.json --factory 0xYOUR_FACTORY --from 0xYOUR_WALLET_ADDRESS
```

Скрипт покажет выбранный маршрут, `predictedCount`, оценку газа и верхнюю границу расходов. Для пакетного маршрута дополнительно проверяются код фабрики, её владелец и получатель. Для отправки:

```sh
read -rs 'PRIVATE_KEY?Приватный ключ: '
export PRIVATE_KEY
node batch.mjs mint --config batch.config.json --send
unset PRIVATE_KEY
```

Платёж за NFT всегда равен **0 ETH**: платный этап не пройдёт симуляцию с нулевой оплатой, а фабрика дополнительно проверяет цену. Один основной кошелёк оплачивает весь газ. При `quantity: 1` он оплачивает только прямую транзакцию минта; при большем количестве — развёртывание фабрики и пакетный минт, включая создание помощников и переводы NFT. Если отправленная транзакция откатится, газ всё равно будет потрачен.

Успешный результат содержит хеш транзакции, фактическое `count` и список `tokenIds`. Для пакета дополнительно выводятся уникальные адреса `helpers` и проверяются события фабрики `TokenMinted`/`BatchMinted`; для прямого минта — события NFT `Transfer` и `SeaDropMint`.

Прямой минт учитывает пожизненный счётчик минта основного кошелька. Если этот кошелёк уже исчерпал лимит этапа, симуляция отклонит вызов. В режиме `quantity: 1` получатель должен совпадать с отправителем: оставьте `recipient: null`.

## Несколько RPC и повторные попытки

Приватный ключ используется локально **один раз для одной транзакции**. Скрипт заранее фиксирует nonce, подписанные байты и хеш. Все RPC получают одинаковую транзакцию; повторная передача этих же байтов не создаёт второй минт в цепочке.

Первый раунд обращается к каждому прошедшему проверку RPC с ограничением `concurrency`. Дополнительные раунды выполняются только пока ни один RPC не подтвердил приём или наличие транзакции с ожидаемым хешем. При ошибке отправки скрипт проверяет транзакцию по её хешу. Во время повторов новый nonce не берётся и новая подпись не создаётся.

До отправки выводятся локально вычисленный хеш и ссылка на обозреватель. **При неопределённом результате или отсутствии receipt сначала проверьте этот хеш.** Новый запуск команды с `--send` может сформировать уже другую транзакцию с новым nonce. Отсутствие ответа от RPC не доказывает, что предыдущая отправка не состоялась.

В Robinhood Chain порядок определяется временем поступления к sequencer; увеличение priority fee не перемещает транзакцию перед уже поступившими. Это описано в [официальной документации о порядке транзакций](https://docs.robinhood.com/chain/differences-from-ethereum/). Публичные RPC имеют ограничения частоты запросов, что отдельно отмечено в [документации подключения](https://docs.robinhood.com/chain/connecting/).

Асинхронного Node.js достаточно для реализованных параллельных RPC-запросов. Ускорение от переписывания этого сценария на Rust не измерялось. Несколько RPC позволяют отправлять запросы одновременно, но не гарантируют более раннее включение в блок.

## Условия минта и проверка кода

- Фабрика работает только с бесплатным **публичным** этапом SeaDrop, при оставшемся выпуске и ненулевом разрешённом количестве на адрес. Она проверяет актуальные условия при каждом вызове.
- Если получатель имеет контрактный код, он должен принимать ERC-721 через `onERC721Received`; иначе безопасный перевод отклонит всю партию.
- Подпись из исходной `mintSigned`-транзакции уже использована и привязана к её получателю. Она не подходит новым помощникам. Batch-режим её не использует.
- `batch.mjs` сравнивает SHA-256 локального Solidity с артефактом сборки, проверяет Solidity 0.8.26 и настройки EVM Shanghai. При изменении исходника пересоберите артефакты: `npm run compile:batch`.
- Перед вызовом существующей фабрики сравнивается её runtime с артефактом, с учётом неизменяемых адресов владельца и получателя. Значения этих адресов затем проверяются через getters.
- Проверяются chain ID 4663, байткод исследованного NFT, наличие SeaDrop, `eth_call` и оценка газа. Проверки используют `latest`, чтобы обычный запуск не требовал архивного RPC; номер блока в отчёте — наблюдавшаяся вершина перед проверками. Условия могут измениться до включения транзакции и повторно проверяются контрактами. Отправка доступна только с `--send`.
- `npm test` проверяет конфиг, оба маршрута, допустимый меньший остаток, runtime, подписи и одинаковые байты через локальные RPC, dry-run, события, ожидание этапа, отмену, тайм-ауты, повторное использование соединений и бенчмарк. Эти проверки не являются подтверждением успешного минта в mainnet.

## Проверка полного пути

Прямой `SeaDrop.mintPublic(...,1)` также успешно проверен read-only вызовом с временным временем публичного этапа, без фабрики и без замены состояния контрактов: [direct-state-override.json](research/direct-state-override.json).

На двух RPC успешно выполнен read-only `eth_call` полного runtime фабрики: `mintBatch(10,10)` вернул `10`. Код фабрики временно подставлялся по пустому синтетическому адресу, время вызова — на начало публичного этапа. Код и состояние Genesis, SeaDrop, registry и обработчика переводов не заменялись. Внутри фабрики проверяется владелец каждого NFT до и после передачи. Результат: [batch-state-override.json](research/batch-state-override.json).

Это симуляция на состоянии сети в момент проверки, без подписи и реальной транзакции. Подстановка времени существует в исследовательских скриптах и бенчмарке `--full`; `batch.mjs` проверяет фактическое время сети. Первоначальный снимок показывал этап 15 сентября 2026, 19:00:20–20:00:20 МСК; расписание может меняться. Режим `mint --wait` читает актуальное расписание из SeaDrop, отслеживает изменения и ждёт открытия по времени блока. Без `--wait` симуляция до открытия отклоняется.

Повторить read-only проверку фабрики:

```sh
npm run simulate:rpc
```

Также пройден тест на локальном Anvil 1.7.1 с архивным состоянием блока **63609112**: один тестовый кошелёк оплатил создание фабрики, 10 помощников сминтили NFT **907–916** и передали все десять тому же кошельку. Проверены уникальность помощников, владение каждым NFT, увеличение выпуска и баланса получателя, лимит одного минта у каждого помощника. Отдельные искусственные сценарии подтвердили получение трёх оставшихся NFT при `max=10/min=1` и полный откат при сломанном обработчике перевода. Отчёт: [batch-simulation.json](research/batch-simulation.json).

Локальный газ: создание фабрики **663256**, партия из 10 — **2259304**. Эти числа не включают специфичную для Robinhood плату за публикацию данных в L1 и не заменяют текущую оценку RPC. В тесте время сдвинуто до публичного этапа; синтетические Anvil-адреса очищены от унаследованного контрактного кода. Код реальных зависимостей для основной проверки десяти минтов не изменялся.

Для воспроизведения нужен современный Anvil и архивный RPC. В двух терминалах:

```sh
anvil --host 127.0.0.1 --port 18548 --chain-id 4663 \
  --fork-url https://robinhood-chain.gateway.tenderly.co/ \
  --fork-block-number 63609112
```

```sh
npm run test:batch -- http://127.0.0.1:18548
```

Скрипт принимает только локальный Anvil, создаёт снимок перед тестом и восстанавливает его после. Исторические чтения и лимиты публичных RPC могут ограничивать повторение fork-теста; диагностика провайдеров сохранена в [batch-archive-diagnostic.json](research/batch-archive-diagnostic.json).
