# Запуск заранее и измерение скорости

## Две команды для обычного запуска

Сначала настройте `batch.config.json` по [шаблону](batch.config.example.json). Для реальной отправки задайте `PRIVATE_KEY` локально в окружении.

**Первый запуск: развернуть фабрику при необходимости, проверить её и запустить ожидание минта:**

```sh
npm run launch -- --config batch.config.json --send
```

Повторный `launch` использует сохранённую фабрику. Если предыдущая отправка деплоя завершилась неопределённо, команда сначала проверяет её результат и может повторить только ту же подписанную транзакцию.

**Последующие запуски с существующей фабрикой:**

```sh
npm run start -- --config batch.config.json --send
```

`start` проверяет фабрику и запускает ожидание. Если готовой фабрики нет, он останавливается; деплой этой командой не выполняется. При `quantity: 1` обе команды сразу используют прямой минт с ожиданием, без фабрики и файла её состояния.

Без `--send` передайте `--from 0xYOUR_WALLET_ADDRESS`: выполнятся проверки и симуляция без отправки. Если фабрики ещё нет, `launch` симулирует деплой и завершится — для дальнейшего ожидания пакетного минта нужен реальный контракт.

## Запуск через sequencer

Команда для полного запуска с прямой отправкой деплоя и минта в sequencer:

```sh
npm run launch:sequencer -- --config batch.config.json --send
```

Для уже развёрнутой фабрики:

```sh
npm run start:sequencer -- --config batch.config.json --send
```

Используйте одну подходящую команду. Нужен локально заданный `PRIVATE_KEY`. Полный [шаблон настроек](batch.config.sequencer.example.json) задаёт максимум 10 NFT, минимум 1, ожидание до 24 часов и потолок резерва `0.08 ETH` **на каждую транзакцию**. Баланс `0.1 ETH` не означает, что две транзакции смогут потратить по `0.08`: перед каждой отправкой проверяется текущий баланс и конкретная комиссия. Конфиг с ключом создавать не нужно.

`launch:sequencer` находит сохранённую фабрику или разворачивает её, дожидается receipt, проверяет код и владельца, затем прогревает соединения и ждёт открытого публичного этапа. При `quantity: 1` сразу готовится прямой минт через SeaDrop. Восстановление незавершённого деплоя также отправляет в sequencer только ранее сохранённую транзакцию.

### Время или блок

Можно добавить к команде `--wait-until-timestamp UNIX_SECONDS` либо `--wait-until-block BLOCK_NUMBER`. Это целые числа, время — Unix timestamp в секундах. То же задаётся в JSON:

```json
{
  "waitUntilTimestamp": null,
  "waitUntilBlock": null
}
```

Замените нужный `null` числом или строкой с десятичным числом. Если задано время, скрипт ждёт времени **последнего блока сети**; если блок — наблюдаемой высоты. Если заданы оба условия, должны выполниться оба. Дополнительно всегда требуется открытое актуальное окно SeaDrop. С `null` скрипт ориентируется только на окно минта. CLI-параметры имеют приоритет над JSON и автоматически включают ожидание в `batch.mjs mint`.

Фабрика разворачивается сразу; заданные цели задерживают только минт. После достижения целей ещё выполняются финальная симуляция, оценка газа, обновление комиссии и nonce, подпись и отправка. Это отправка **после наблюдения** нужного блока/времени: она не резервирует позицию и не гарантирует включение в конкретный блок. Пользовательские цели проверяет процесс на сервере; контракт по-прежнему проверяет реальное окно SeaDrop и доступный остаток. Изменять Solidity или заново разворачивать существующую фабрику для этого режима не требуется.

### Какие запросы куда идут

| Назначение | Endpoint |
| --- | --- |
| Отправка подписанного деплоя и минта | `https://sequencer.mainnet.chain.robinhood.com` |
| Прогрев той же связи с sequencer | `arb_checkPublisherHealth` |
| Chain ID, блоки, состояние, nonce, комиссия, симуляция, поиск транзакции и receipt | Обычные RPC из `rpcUrls` / `--rpc` |

Адрес sequencer указан в [документации Robinhood](https://docs.robinhood.com/chain/connecting/). В [сохранённой проверке](research/sequencer-capabilities.json) health и обработчик отправки доступны, чтение блоков и chain ID на этом endpoint недоступны. Успешный health возвращает `null`. Проверялись read-only методы и один заведомо пустой некорректный raw; реальная транзакция в рамках проверки не отправлялась.

Новый транспорт также прошёл [проверку подключения к mainnet](research/sequencer-smoke.json): health через sequencer, chain ID и блок через read RPC, без подписи и отправки. `npm test` проверяет полный CLI-цикл на отдельных локальных RPC/sequencer: деплой → сохранение → ожидание двух границ → минт 10, повторное использование фабрики, прямой минт 1, потерянный ответ и восстановление, ограничения газа, отмену и keep-alive. Эти тесты не измеряют включение транзакции в mainnet.

Режим включается флагом `--sequencer` или `"sequencer": true`. Для явно выбранного другого Nitro endpoint есть `--sequencer-url URL` / `sequencerUrl`; он должен поддерживать `arb_checkPublisherHealth` и `eth_sendRawTransaction`. Этот адрес не нужно добавлять в `rpcUrls`. В режиме sequencer отправка идёт только в выбранный send endpoint, без автоматической рассылки через обычные RPC; `attempts` и `retryDelayMs` ограничивают повторение тех же подписанных байтов. `concurrency` сохраняется для обычного режима с несколькими RPC, у единственного sequencer отправка одна.

Потерянный ответ проверяется по локальному хешу через read RPC. Пока результат неизвестен, ошибка не означает, что отправка не состоялась. Для деплоя сохранённое состояние позволяет продолжить тот же запуск; при неопределённом результате минта проверьте напечатанный хеш перед новым запуском. Прямой маршрут исключает пересылку транзакции выбранным публичным RPC, но преимущество по задержке и место в гонке нужно измерять отдельно.

Без `--send` и с `--from 0xYOUR_WALLET_ADDRESS` команда делает dry-run. При отсутствии фабрики она симулирует только деплой и завершает работу. С существующей фабрикой она ждёт заданных условий, симулирует минт и завершает работу без подписи/отправки.

### Где сохраняется фабрика

Адрес хранится автоматически в каталоге проекта:

```text
.state/factory-4663-0xАДРЕС_КОШЕЛЬКА_В_НИЖНЕМ_РЕГИСТРЕ.json
```

Файл привязан к сети, владельцу, получателю и версии Solidity-артефакта. Изменение количества минта не требует новой фабрики. Пользовательский JSON-конфиг не перезаписывается. Если в нём уже указан `factory` либо передан `--factory`, `launch`/`start` проверят этот адрес и сохранят его; конфликт с ранее сохранённым адресом остановит запуск.

Перед первой отправкой деплоя атомарно сохраняются предполагаемый адрес фабрики, nonce, хеш и подписанная транзакция. Приватного ключа в файле нет. После подтверждения кода, владельца и получателя состояние становится `deployed`, подписанные байты удаляются из файла. При ошибке RPC или тайм-ауте запись остаётся для восстановления. Если старый nonce уже занят неизвестной транзакцией, деплой откатился или сохранённый код не совпал, автоматического создания другой фабрики не будет.

Рядом создаётся `.lock`, который удерживается до завершения деплоя, ожидания и минта. Второй `launch`, `start` или `deploy` с тем же файлом состояния не сможет работать одновременно. При обычном завершении и `Ctrl+C` блокировка снимается. После `SIGKILL` или перезапуска сервера `.lock` может остаться: проверьте указанные в ошибке PID/host и отсутствие работающего процесса, затем удалите **только `.lock`**. JSON состояния для повторного запуска удалять нельзя.

При необходимости можно явно передать `--state-file /path/factory.json`. Используйте один и тот же файл для одного кошелька во всех командах. При переносе на дедик перенесите JSON состояния после остановки старого процесса; `.lock` переносить не нужно. Независимые файлы на разных серверах не дают общей блокировки. Старый низкоуровневый `batch.mjs mint --factory ...` не участвует в этой блокировке, поэтому не запускайте его параллельно с launcher для того же кошелька.

Отдельная команда деплоя тоже сохраняет и повторно использует фабрику:

```sh
npm run batch -- deploy --config batch.config.json --send
```

Она завершает работу после проверки фабрики, без ожидания минта.

## 1. Настройки

Используйте [batch.config.example.json](batch.config.example.json) как шаблон для своего `batch.config.json`. Подготовка кошелька описана в [BATCH.md](BATCH.md). При `quantity: 1` фабрика не нужна. При большем количестве `launch` разворачивает и сохраняет её автоматически; старые команды прямого вызова требуют адреса в конфиге или `--factory`.

Параметры ожидания и комиссии в шаблоне:

```json
{
  "maxFeeMultiplier": 4,
  "maxGasCostEth": "0.003",
  "waitTimeoutSeconds": 21600,
  "pollIntervalMs": 250,
  "keepAliveIntervalMs": 10000
}
```

Этот фрагмент нужно добавить к остальным настройкам; полный конфиг находится в шаблоне.

- `maxFeeMultiplier: 4`: `maxFeePerGas = 4 × baseFee + maxPriorityFeePerGas`. Это запас по допустимой цене газа; фактическая комиссия определяется сетью. Если поле отсутствует, применяется прежний множитель `2`.
- `maxGasCostEth: "0.003"`: общий потолок `gasLimit × maxFeePerGas` на одну транзакцию. При превышении скрипт останавливается до подписи. Увеличение этого потолка само по себе не повышает предлагаемую цену газа.
- `gasLimit` по-прежнему равен оценке RPC с запасом 20%. Множитель цены и запас количества газа — разные настройки.
- Перед отправкой проверяется реальный предел транзакции `ArbGasInfo.getMaxTxGasLimit()`: большой `gasLimit` в заголовке Nitro не заменяет эту проверку. Чтение выполняется параллельно с запросом комиссии; при недоступном пределе отправка останавливается.
- `waitTimeoutSeconds`: максимум подготовки и ожидания после первичной проверки RPC. По умолчанию 6 часов, разрешено до 24 часов. Финальная симуляция и отправка выполняются после этого этапа.
- `pollIntervalMs`: пауза между чтениями времени блока в последние 15 секунд перед стартом. К ней прибавляется время ответа RPC.
- `keepAliveIntervalMs`: период обновления условий минта и фоновых проверок соединений. Вдали от старта опрос идёт с этим интервалом.

### Сколько ETH держать на газ

Для десяти NFT и `maxGasCostEth: "0.003"` практический баланс с запасом: **0.007 ETH**, если нужны деплой и минт, либо **0.004 ETH**, если фабрика уже есть. Самими лимитами ограничено соответственно до 0.006 ETH на две транзакции и до 0.003 ETH на одну. Это резерв под выбранные настройки, а не плата за минт и не гарантия выполнения при любой нагрузке.

При неизменной оценке `gasLimit = 3044499` партия из десяти при `maxFeePerGas = 1 gwei` требует резерв 0.003044499 ETH и уже не пройдёт лимит 0.003. При 3 gwei резерв был бы 0.009133497 ETH. Дополнительный баланс на кошельке не повышает лимит в конфиге. Цена газа и оценка RPC меняются; перед отправкой скрипт получает их заново.

Свежая проверка 15 сентября 2026, около 15:52 МСК: base fee около 0.066052 gwei, priority fee 0. При множителе 4 и прежних оценках газа суммарный расчётный резерв для деплоя и десяти минтов — около 0.001017 ETH. Исходные RPC-ответы, арифметика и ограничения: [gas-budget-latest.json](research/gas-budget-latest.json). Документация описывает [динамическую комиссию L2 и публикацию данных в L1](https://docs.robinhood.com/chain/gas-and-fees/); гарантированный будущий максимум цены газа в исследованных документах не установлен.

**Резерв 0.1 ETH на балансе** не меняет ограничения в конфиге. Для партии с `gasLimit = 3044499` он позволяет зарезервировать не больше примерно 32.846 gwei за единицу газа, если нет других расходов. При множителе 4 это соответствует base fee около 8.212 gwei. Если base fee выше, скрипт может остановиться по балансу из-за запаса по `maxFeePerGas`, хотя стоимость исполнения по текущей base fee была бы меньше. Повышение `maxGasCostEth` разрешает больший расход; уменьшение множителя снижает запас на рост цены после подписи.

Отдельный явный профиль для резерва **0.1 ETH** и количества **10**: [batch.config.reserve.example.json](batch.config.reserve.example.json). В нём `maxFeeMultiplier: 2` и `maxGasCostEth: "0.08"`. Это разрешает **до 0.08 ETH газа на одну транзакцию**, а не фиксирует такую плату. При цене газа 11.492786 gwei и прежних gas limit резерв составил бы около 0.069980 ETH для минта и 0.018472 ETH для деплоя. Множитель 2 оставляет меньший запас на дальнейший рост цены после подписи, чем множитель 4. Баланс, текущая симуляция и оценка газа всё равно проверяются перед каждой отправкой.

Этот профиль используется только при явном `--config batch.config.reserve.example.json`; действующий пользовательский конфиг не изменялся. Перед запуском проверьте `quantity` и получателя. Выберите одну команду.

Создать или использовать сохранённую фабрику, затем ждать и минтить:

```sh
npm run launch -- --config batch.config.reserve.example.json --send
```

Использовать только уже готовую фабрику, затем ждать и минтить:

```sh
npm run start -- --config batch.config.reserve.example.json --send
```

Первая команда создаёт или использует сохранённую фабрику, вторая требует уже готовую фабрику. Применяйте нужную команду один раз; обе команды с `--send` при открытии этапа могут отправить отдельный минт.

Исторические значения в обозревателе требуют проверки: `gasPrice` у некоторых транзакций отличается от `effectiveGasPrice` в receipt. Для фактической комиссии используйте `receipt.gasUsed × receipt.effectiveGasPrice`. Сохранены [история графиков](research/gas-history-charts.json) и [пример расхождения, проверенный двумя RPC](research/gas-history-explorer-anomaly.json). Из максимума на графике нельзя автоматически выводить рекорд уплаченной комиссии.

Результаты проверки перегрузки 4 сентября, фактические комиссии и границы выборки: [GAS_HISTORY.md](research/GAS_HISTORY.md).

Первым в `rpcUrls` поставьте подходящий RPC по замерам с сервера. Он используется для ожидания, финальной симуляции и nonce. При ошибках чтения во время ожидания возможен переход на резервный RPC. В обычном режиме подготовленные резервные RPC также участвуют в рассылке; для одновременной отправки на все адреса задайте `concurrency` не меньше числа RPC (максимум 8). В режиме sequencer этот список используется для чтений, а отправка идёт напрямую в выбранный sequencer.

## 2. Запуск до открытия этапа

Например, за 5–15 минут до ожидаемого начала. Проверка без отправки и без приватного ключа:

```sh
npm run batch -- mint --wait --config batch.config.json --from 0xYOUR_WALLET_ADDRESS
```

Команда остаётся запущенной до открытия публичного этапа. Затем выполняет настоящие `eth_call` и `eth_estimateGas` на текущем состоянии сети, выводит результат и завершает работу.

Для **автоматической отправки при открытии** заранее задайте `PRIVATE_KEY` локально и добавьте `--send`:

```sh
npm run batch -- mint --wait --config batch.config.json --send
```

Скрытый ввод ключа для zsh приведён в [BATCH.md](BATCH.md). Ключ не записывается в конфиг. `--send` разрешает одну реальную транзакцию после успешных проверок; дополнительного запроса подтверждения при открытии этапа нет.

Режим выполняет следующие действия:

1. Проверяет chain ID, код NFT/SeaDrop и, для партии, код фабрики, владельца и получателя. Готовит calldata для каждого прошедшего проверку RPC.
2. Читает актуальные условия бесплатного публичного этапа и остаток выпуска. Использует те же HTTP keep-alive соединения, периодически проверяет RPC. Сервер может закрыть простаивающее соединение; тогда пул установит новое.
3. Ждёт начала по **времени блоков**, повторно читает расписание при открытии. При переносе старта продолжает ожидание в пределах тайм-аута. Платный, отключённый, завершённый этап или недостаточный остаток останавливают запуск.
4. Обновляет chain ID и блок, параллельно выполняет финальную симуляцию и оценку газа. Затем получает комиссию, баланс и `pending` nonce; независимые запросы выполняются параллельно.
5. При `--send` подписывает одну транзакцию и рассылает одинаковые байты через RPC. После этого проверяет receipt и события минта.

Статические проверки кода и неизменяемых адресов не повторяются перед отправкой. Финальная симуляция использует актуальное состояние и **не подменяет время блока**. Условия всё ещё могут измениться между симуляцией и исполнением; успешная симуляция не гарантирует минт.

`Ctrl+C` или `SIGTERM` прерывают ожидание и закрывают RPC-соединения. Если отправка уже началась, остановка процесса не отменяет транзакцию: сначала проверьте напечатанный хеш. Запускайте один отправляющий процесс на кошелёк, чтобы независимые процессы не конкурировали за nonce. Конфиг читается один раз при старте; изменение файла во время ожидания не меняет подготовленную транзакцию. Автоматического повышения комиссии и замены pending-транзакции нет.

## 3. Бенчмарк с текущей машины или будущего сервера

Команды работают **без ключа, ETH и развёрнутой фабрики**. Из конфига бенчмарк использует только `rpcUrls` и `quantity`.

Чтение RPC и локальные кодирование/подпись:

```sh
npm run benchmark -- --config batch.config.json --samples 20 --output benchmark.json
```

Дополнительно симуляция полного минта и оценка газа:

```sh
npm run benchmark -- --config batch.config.json --samples 20 --full --full-samples 3 --output benchmark-full.json
```

До создания собственного конфига можно передать `--config batch.config.example.json`. Для прямого минта добавьте `--quantity 1`; для партии — нужное количество, например `--quantity 10`.

Каждый RPC измеряется отдельно, RPC работают параллельно. `--interval-ms 250` задаёт минимальный интервал между началами запросов к одному endpoint; одновременно на него идёт не больше одного запроса. Запросы имеют тайм-аут. Отчёт печатается в JSON и сохраняется в `--output`; существующий файл не перезаписывается, для следующего запуска выберите другое имя.

| Поле отчёта | Что измеряет |
| --- | --- |
| `coldConnectAndChainRead` | Первый запрос chain ID, включая установку соединения. Системные DNS/TLS-кеши могут быть уже прогреты. |
| `warm` | Последующие запросы `eth_blockNumber` через пул соединений. |
| `full.ethCall` | Время симуляции прямого минта либо всей партии. |
| `full.ethEstimateGas` | Время оценки газа того же вызова. |
| `offline.coldSign` / `offline.warmSign` | Первая операция с созданием тестового кошелька и последующие локальные подписи. Подписанные байты отбрасываются. |
| `p50Ms` / `p95Ms` | Медиана и 95-й процентиль успешных запросов, в миллисекундах. |
| `successes` / `errors` / `errorCounts` | Число успешных запросов и ошибки; ошибки не попадают в статистику успешных задержек. |

`--full` временно задаёт время начала публичного этапа только внутри read-only RPC-запросов. Для партии по синтетическому адресу подставляется runtime фабрики; реальные зависимости остаются неизменными. Поэтому этот режим доступен до открытия этапа и до развёртывания своей фабрики. Он проверяет строго `quantity` минтов: при меньшем остатке, неподдерживаемых RPC-подстановках или откате будет ошибка. Это не симуляция конкретного пользовательского кошелька.

Бенчмарк **не отправляет транзакции**. Он измеряет RPC, симуляцию и локальную обработку, но не время поступления к sequencer или включения в блок. Несколько удачных запросов не доказывают стабильную скорость; сравнивайте также ошибки и повторяйте замеры в сопоставимые временные окна.

Проверочный короткий запуск с локальной машины: [benchmark-local-readonly.json](research/benchmark-local-readonly.json), 15 сентября 2026, 15:12 МСК. Три прогретых чтения дали медиану около 100 мс у PublicNode и 2988 мс у официального RPC; одна симуляция партии из десяти заняла соответственно 158 и 2555 мс. Это небольшая выборка с конкретного подключения, а не результат будущего дедика.

## 4. Замеры самого запуска

`batch.mjs` выводит `timingsMs`, в том числе после ошибки:

- `rpcChecks`, `prepareAndWait` — первичные проверки, подготовка и ожидание.
- `ethCall`, `estimateGas`, `gasQuote`, `walletRefresh`, `signing` — длительности соответствующих шагов.
- `readyToBroadcast` — время от обнаружения открытого этапа до начала рассылки; включает финальные проверки. Это не задержка относительно объявленного времени старта.
- `firstRpcAcknowledgement` — от начала рассылки до первого подтверждения приёма либо наличия хеша у RPC.
- `broadcastAllSettled` — до завершения всех предусмотренных попыток; медленный резервный RPC может увеличить это число после успешной отправки основному.
- `receiptAfterBroadcastSettled` — ожидание receipt после завершения рассылки. Оно зависит от опроса и не равно времени включения в блок.
- `total` — длительность процесса обработки RPC, начиная после чтения конфига, артефакта и создания кошелька. Параллельные шаги перекрываются, поэтому их длительности нельзя просто складывать.

Метрики отправки появятся только при настоящем `--send`. Проверка `npm test` использует локальные RPC и синтетические ключи, включая полный CLI-путь ожидания и рассылки для обоих маршрутов.

## 5. Перенос на сервер

На будущем сервере сначала установите зависимости, выполните `npm test` и повторите две команды бенчмарка с теми же RPC. По результатам выберите основной endpoint и сравните сервер с локальной машиной. Для первой установки достаточно одного процесса Node.js; выигрыш от другого языка или нескольких серверов нужно подтверждать этими замерами.

Полная RPC-нода Robinhood и среда Node.js — разные компоненты. Установка полной ноды потребует отдельной проверки требований к серверу и синхронизации. В текущем изменении добавлены команды для локального запуска и будущего переноса; удалённая установка ещё не выполнялась.
