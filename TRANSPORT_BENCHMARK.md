# Node, Rust и собственный WebSocket: один запуск

Команда запускает пять клиентов на одной машине: Node/Rust HTTPS health, Node WebSocket feed, Rust WebSocket через `tokio-tungstenite` и Rust с собственным разбором кадров (`raw`). Сохраняет сырые измерения и печатает p50/p95/p99.

Это тест без кошелька и транзакций. HTTPS health и feed ping/pong — **разные операции**, их результаты не означают скорость включения транзакций.

## Подготовка

Node 22, Python 3.9+ и Rust 1.88+. Сборки выполняются до измерений:

```bash
npm ci --prefix websocket-sequencer-probe --ignore-scripts --no-audit --no-fund
cargo build --release --locked --jobs 1 --manifest-path rust-sequencer-probe/Cargo.toml
cargo build --release --locked --jobs 1 --manifest-path rust-websocket-probe/Cargo.toml
```

## Пять клиентов одной командой

Из корня проекта:

```bash
python3 transport-benchmark.py --duration-seconds 600 --output-dir .state/transport-run-01
```

Каталог должен быть новым; для следующего прогона меняйте имя. Приватные ключи и `.env` не нужны. Нужную версию Node можно указать через `--node /path/to/node`. Для готовых бинарников доступны `--rust-http-bin` и `--rust-ws-bin`.

Команда получает актуальные IPv4 официальных endpoint и закрепляет один адрес для обоих HTTPS-клиентов и один для всех трёх WebSocket-клиентов. Host, SNI и проверка TLS остаются исходными. Опции `--http-ip` и `--ws-ip` выбирают адрес из текущего DNS-набора. Не переносите фиксированный IP навсегда в рабочий конфиг.

Старт примерно через 20 секунд, запросы раз в секунду, timeout 5 секунд. Прогрев исключается; небольшие сдвиги фаз распределяют отправку по времени. Статистика пересчитывается в общем временном окне отдельно для HTTP и WSS. Ошибки не становятся нулевыми задержками; поздние ответы остаются в выборке, если запрос начался внутри окна.

Выходные файлы: `manifest.json`, пять JSON/логов клиентов, `exits.json`, `comparison.json`. Код выхода 0 — все выборки пригодны, 2 — недостаточные/неполные выборки, 1 — ошибка запуска или входных данных. Короткий `--duration-seconds 30` проверяет работоспособность, но не p99; ожидаемый код — 2 из-за малого числа проб.

## Rust WebSocket отдельно

```bash
rust-websocket-probe/target/release/rust-websocket-probe \
  --engine raw --label ohio-raw --duration-seconds 600 --output raw-feed.json
```

Для библиотечного варианта заменить `raw` на `tungstenite`. Оба используют одно постоянное TCP/TLS-соединение, `TCP_NODELAY`, `rustls` и одинаковые ping payload. Сжатие отключено. При разрыве тест завершается с неполным отчётом; скрытых переподключений нет.

Собственная реализация в `rust-websocket-probe/src/raw.rs` проверяет upgrade, маски, фрагментацию, UTF-8, ping/pong/close и ограничения размера. Частично прочитанные данные сохраняются при отмене операции. Feed считается и отбрасывается порциями, без накопления сообщения целиком. TLS, стандартный SHA-1 accept-key и случайные маски используют библиотечные примитивы. Это специализированный измерительный клиент, без отправки NFT-транзакций по WSS.

## Как читать результат

- Rust HTTPS **уже переиспользовал** клиент и соединение. Новые `connectionStats` показывают DNS/TCP/TLS/HTTP счётчики, включая прогрев.
- Более низкая медиана не означает лучший p95/p99. Смотрите ошибки, фактические IP, переподключения и число проб.
- Один IP балансировщика ещё может вести к разным внутренним процессам. Node/OpenSSL и Rust/rustls отличаются не только языком.
- Все пять клиентов работают одновременно. Feed и две дополнительные cold HTTPS-пробы Node за 600 секунд добавляют нагрузку.
- Собственный codec может снизить выделения памяти и работу клиента, но не устраняет задержку сервера/маршрута и ожидание предыдущих данных в TCP.
- Около 600 проб дают лишь несколько наблюдений в верхнем 1% хвосте. Для уверенных выводов нужны повторения.
- Переиспользование соединений влияет на сеть и CPU. Газ контракта от выбора языка или транспорта не уменьшается.
